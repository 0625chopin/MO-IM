## 1. I-055 — 오류 추적(NFR-028)이 Sentry 계정·DSN 부재로 미완결

### 1.1 무엇이 도착하면 닫히는가

**`SENTRY_DSN`(및 조직/프로젝트 slug 등 부수 환경변수) 값 하나가 도착하면 닫힌다** — 계정
생성 여부·조직 이름 같은 부수 정보는 판정에 필요 없다. DSN 문자열 자체가 유일한 입력이다.

### 1.2 도착 즉시 실행할 절차와 판정 기준

1. `SENTRY_DSN`을 `.env.local`(로컬)·Vercel 환경변수(배포)에 채운다.
2. `@sentry/nextjs`를 공식 설치 마법사(Next.js 16 문서 기준, Turbopack 대응 확인)로 설치하고
   `instrumentation.ts`류 파일을 생성한다 — **이 단계에서 새 의존성이 추가되므로 팀장 승인이
   먼저 있어야 한다**(이번 회차 배정 지시 "npm 패키지를 새로 설치하지 마라"가 여전히 유효한
   기본값이고, DSN 도착이 그 예외를 여는 트리거다).
3. `src/lib/audit/error-tracking.ts`의 `captureError` **본문만** `Sentry.captureException(...)`
   호출로 교체한다 — 아래 1.3에서 확인했듯 이 함수가 유일한 교체 지점이므로 호출부
   (`report-client-error.ts`, `error.tsx`·`global-error.tsx`·`sample/error.tsx`)는 시그니처가
   바뀌지 않는 한 손대지 않는다.
4. `npm run build`로 Turbopack 빌드 통과를 실제로 검증한다(팀장 전용 운영 규칙 — 팀장이
   실행한다).

**판정 기준**:

| 도착한 값·결과 | 판정 |
| --- | --- |
| DSN 유효 + 위 ①~④ 완료 + `npm run build` 통과 | **I-055 해소** — Sentry 완전 도입 |
| DSN 유효 + ①~③ 완료했으나 `npm run build`가 Turbopack에서 실패 | **부분 해소** — 연결 자체는 끝났지만 빌드 호환성이 별개 결함이다. 원인(예: `withSentryConfig`와 Turbopack 최상위 `turbopack` 설정 충돌)을 새 이슈로 draft에 등재하고 이번 이슈는 그 이슈로 대체 승계 |
| 계정만 생성되고 DSN 미발급, 또는 DSN 발급이 다음 회차로 또 미뤄짐 | **(C) 유지** — 임시 구조화 `console.error` 구현을 그대로 쓴다. 재조사 불필요, 이 문서가 다음에도 그대로 유효하다 |

재조사가 필요 없는 이유: 위 절차·판정 기준이 코드를 직접 읽어(1.3) 이번에 확정한 것이라,
다음에 이 건을 집는 사람은 DSN 값만 받아 ①~④를 실행하면 끝난다.

### 1.3 팀이 지금 확인해 둔 것 — 어댑터 경계 실측과 판단

**`captureError`(`src/lib/audit/error-tracking.ts`)가 실제로 유일한 교체 지점인지 코드로
확인했다.** 이 함수를 호출하는 곳은 프로젝트 전체에 **`report-client-error.ts` 단 1곳**뿐이고
(`grep -rn "captureError"` 결과 `error-tracking.ts` 자신을 빼면 이 파일 하나), 그 Server
Action은 `error.tsx`(`(shell)`)·`global-error.tsx`·`sample/error.tsx` 3개 오류 경계가
공유한다. 즉 **"DSN만 꽂으면 되는 형태"라는 어댑터 경계는 이미 있다** — 새로 만들 필요가
없다는 것이 이번 회차의 판단이다(어댑터를 새로 만드는 쪽이 항상 옳지 않다는 배정 지시에 대한
답).

**단, 이 경계의 적용 범위를 정확히 해 둔다 — 넓지 않다.** `grep -rn "console\.error"`로
전수 조사한 결과 프로젝트에는 이 경계를 거치지 않는 **구조화되지 않은 `console.error` 호출이
정확히 18곳** 더 있다(세는 방식: 실제 호출 표현식만 센다 — docstring 안에서 `console.error`를
글로만 언급한 3곳(`audit-log.ts`·`error-tracking.ts`·`realtime/types.ts`의 주석)은 호출이
아니라 제외했고, `error.tsx`(`(shell)`)·`global-error.tsx`·`sample/error.tsx`의
`console.error(error)`도 제외했다 — 이 셋은 **같은 컴포넌트가 바로 다음 줄에서
`reportClientErrorAction`을 호출해 이미 이 어댑터를 거치므로**, 브라우저 콘솔에 남는 그
한 줄은 "포착되지 않은 오류"가 아니라 이미 포착된 오류의 부가 echo다):

- Realtime 구독 오류(4곳): `MessageRoomContainer.tsx`·`use-notification-feed.ts`·
  `ToastHostContainer.tsx`·`PollLiveContainer.tsx`의 `[chat]`/`[notifications]`/`[poll]`
  접두 로그
- 채팅 자체 동작 실패(3곳): `MessageRoomContainer.tsx`의 전송 실패·삭제 실패·읽음 지점 갱신 실패
- 부수 알림 발송 실패, fire-and-forget `.catch()`(7곳): `cancel-meetup.ts`·`create-comment.ts`·
  `disband-crew.ts`·`remove-crew-member.ts`·`transfer-crew-ownership.ts`(2곳)·`withdraw-poll.ts`
- **poll 자동 종료(트리거③) 실패(1곳)**: `cast-vote.ts:111` — 투표 저장 자체는 이미 성공한
  뒤 "전원 투표 완료 시 자동 종료" 후속 시도가 실패해도 표는 되돌리지 않고 로깅만 한다
  (마감 시각 도래 트리거①이 결국 마무리하므로 안전하다는 설계 의도가 주석에 있다)
- 감사·이벤트 기록 실패(2곳): `audit-log.ts`("audit_logs insert 실패")·`product-event.ts`
- Realtime auth 토큰 갱신 재시도 소진(1곳): `realtime/broadcast.ts`

**판단**: 지금 이 18곳까지 묶는 더 넓은 어댑터를 만들지 않는다. NFR-028의 측정 기준(요구사항
문면)은 "클라이언트·서버 오류를 사용자·크루·요청 식별자로 추적"이며, 18일차 Task 038이 이미
그 기준을 **오류 경계(렌더 크래시) 캡처**로 좁혀 구현 범위를 잡았다(`ops-foundation-038.md`
§3, I-055 원문). 위 18곳은 대부분 "실패해도 주 흐름을 막지 않는" 부수 효과 실패
(fire-and-forget 알림, 감사 로그 적재, poll 자동 종료 재시도 실패)이거나 이미 사용자에게
도메인 오류로 보여준 뒤의 보조 디버그 로그(Realtime 구독 실패는 `onError` 콜백으로 화면에
이미 노출된다, D-030 ③)라 **같은 정도로 급하지 않다.** 지금 범위를 넓히면 "DSN 도착 시 한
줄만 고치면 된다"는 이번 절차의 전제(1.2 ③)가 깨지고, 요구사항 문면이 요구하지 않은 확장을
팀이 임의로 결정하는 것이 된다 — **범위 확장은 하지 않되, 이 사실 자체를 기록해 다음에
NFR-028 범위를 재논의할 사람이 "18곳이 이미 있다"는 걸 다시 조사하지 않게 남긴다.**

### 1.4 팀이 할 수 없는 것

- Sentry 계정 생성·DSN 발급 — 외부 자격증명이라 팀 권한 밖이다(I-016·이메일 템플릿 대시보드
  설정과 같은 유형).
- `@sentry/nextjs` 설치 — 이번 회차 배정 지시가 새 의존성 추가를 금지했다. DSN이 오기 전에
  미리 설치해 두는 것도 의미가 없다(DSN 없이는 초기화가 실패하거나 개발 모드로만 동작해
  "완결"을 증명하지 못한다).
- `npm run build`로 Turbopack 호환성 사전 검증 — 팀 운영 규칙상 build/dev 실행은 팀장
  전용이고, 애초에 DSN 없이는 의미 있는 검증이 안 된다(설치는 되지만 실제 전송 경로 검증은
  DSN이 있어야 한다).

## 2. I-094 — Realtime 월과금 추정치·실제 요금제 미확인

### 2.1 무엇이 도착하면 닫히는가

**사용자가 Supabase 대시보드(Project Settings → Billing/Subscription)에서 확인한 현재
요금제 이름(Free / Pro / Pro 지출 상한 해제 / Team 이상) 한 마디만 있으면, 아래 2.2의 표에
대입해 재조사 없이 즉시 판정이 끝난다.**

### 2.2 도착 즉시 적용할 판정 기준

전제(이미 D-057로 확정, 재확인 불필요): NFR-006(크루당 100세션·전체 1,000세션)을 만족하려면
**연결 상한이 Pro(지출 상한 해제, 10,000) 이상**이어야 한다 — Free(200)·Pro(500) 둘 다 산술적으로
미달.

| 확인된 요금제 | 연결 상한 판정 | 월간 과금 위험(아래 2.3 실측 기준) |
| --- | --- | --- |
| Free | NFR-006 목표 미충족 — 업그레이드 필요(재확인일 뿐, 이미 D-057이 내린 결론) | 현재 실사용 규모에서는 **위험 없음**(2.3) |
| Pro(일반) | NFR-006 목표 미충족 — 업그레이드 필요 | 위험 없음 |
| Pro(지출 상한 해제) | **D-057 목표 이미 충족 — 조치 불필요** | 위험 없음, 조치 불필요 |
| Team / Enterprise | 목표 이미 충족(연결 상한이 그 이상) | 위험 없음, 조치 불필요 |

**즉, 요금제가 무엇으로 확인되든 "월간 과금이 지금 당장 초과되고 있는가"라는 I-094의 ②
질문은 이 문서로 이미 닫힌다(아래 2.3) — 확인이 필요한 것은 오직 "①연결 상한이 목표를
만족하는 플랜인가"뿐이고, 그건 사용자가 대시보드를 보는 것으로 끝난다.** 목표에 못 미치는
플랜이라면 업그레이드는 이미 D-057이 내린 결정을 집행하는 것이지 새로 판단할 것이 없다.

### 2.3 팀이 지금 코드·DB에서 실측해 둔 것

**(a) 메시지 발생 경로 — 코드 전수 확인, 4개뿐이다.** `realtime.send()`를 호출하는 트리거는
마이그레이션 3개 파일에 정확히 4종이다(그 외 없음, `grep -rln "realtime.send" supabase/migrations`
로 확인):

| 트리거 | 토픽 | 발생 시점 |
| --- | --- | --- |
| `chat_messages_broadcast_trigger` | `crew:{crewId}:chat` | 메시지 전송(INSERT)·삭제(041, UPDATE로 확장) |
| `notifications_broadcast_trigger` | `user:{recipientId}:notifications` | 알림 적재(INSERT), 044에서 뮤트 설정 시 조건부 억제 추가 |
| `poll_votes_broadcast_trigger` | `crew:{crewId}:polls` | 투표(INSERT) |
| `polls_broadcast_trigger` | `crew:{crewId}:polls` | 투표 상태 변경(UPDATE, 예: 종료) |

**(b) 동시 구독 형태 — 클라이언트 1개가 여는 실제 채널 수는 3을 넘지 않는다(코드 호출
횟수는 그보다 많지만 라이브러리가 dedup한다).** `subscribeToRoom` 호출부를 전수 확인한
결과: 알림(`user:{id}:notifications`) 토픽은 `NotificationBellContainer`(헤더,
`use-notification-feed.ts` 경유)와 `ToastHostContainer`(`(shell)/layout.tsx`에 상시 마운트)
**둘이 각자 독립적으로 `subscribeToRoom`을 호출**한다. 그런데 설치된 `@supabase/realtime-js`
소스(`RealtimeClient.js` `channel()`)를 확인한 결과 **같은 topic 문자열의 채널이 이미 있으면
새로 만들지 않고 기존 채널을 그대로 반환**한다 — 즉 이 둘은 **실제로는 채널 1개를 공유**하고,
그 위에 각자의 `.on("broadcast", …)` 콜백만 추가로 걸린다(수신 시 로컬에서 콜백 2개가 함께
불릴 뿐, 서버로 보면 구독자는 1개다). 이 dedup·이중 구독의 부작용(두 번째
`subscribe()` 호출의 상태 콜백이 조용히 무시되는 문제)은 I-082 재조사로 새로 확정해 그쪽
문서에 남겼다 — **여기서 중요한 결론은 "실제 채널 수"이지 "호출 횟수"가 아니라는 것**이다.
여기에 특정 채팅방(`MessageRoomContainer`) 또는 특정 투표(`PollLiveContainer`)를 보고 있을
때 채널이 최대 1개 더 열린다 — **로그인 세션 1개가 실제로 여는 채널은 최대 2~3개**이고,
연결당 채널 상한(Free/Pro/Team 공통 100)에는 어느 플랜에서도 여유가 크다. 이 한도는 이번
문제의 병목이 아님을 코드로 확정했다.

**(c) 현재 DB 실측값 — 실 사용량이 아니라 시드/테스트 데이터의 규모다(043B와 같은 caveat).**
`execute_sql`로 직접 집계했다:

| 항목 | 값 |
| --- | --- |
| 크루 총수 / 활성 | 14 / 13 |
| 크루당 활성 멤버십 평균 / 최대 | 3명 / 5명 |
| `chat_messages` 총 행수 (2026-07-15~07-24, 9일) | 132 |
| `notifications` 총 행수 | 47 |
| `poll_votes` 총 행수 | 212 |
| `polls` 총 행수 | 62 |

**팬아웃 배수는 토픽 종류별로 다르게 적용한다** — 위 (b)에서 확인했듯 `notifications`는
사용자 1명당 토픽 1개이고, 이중 마운트는 라이브러리 dedup으로 서버가 실제로 보내는
메시지 수를 늘리지 않는다(로컬 콜백 중복 호출일 뿐, 과금 대상인 "서버 전송 메시지"는
늘지 않는다) — 그래서 `notifications`는 **배수 없이 그대로(×1)** 센다. 반면
`chat_messages`·`poll_votes`·`polls`는 크루(최대 활성 멤버십 5명)에 브로드캐스트되므로
그 인원수만큼 배수를 적용한다:

- 크루 스코프(`chat_messages`+`poll_votes`+`polls` = 132+212+62 = 406건) × 크루당 최대
  구독자 5명 = **2,030건**
- 사용자 스코프(`notifications` = 47건) × 1 = **47건**
- 합계 ≈ **2,077건**(9일 관측분)

이 규모는 **어느 플랜의 초당 한도(최소 Free 100/s)에도, 월간 500만 건 quota에도 근접하지
않는다.** 037이 가정 기반으로 추정한 "크루 10개·10시간/일 활동 시 월 1,818만 건"(과금 초과
가능 시나리오)은 **지금 실제로 존재하는 크루 수(14개)·활동량과는 자릿수가 다른 가정**이며,
그 가정 자체를 확인할 실 트래픽이 여전히 없다는 사실은 이번에도 바뀌지 않았다 — 다만
"지금 당장" 질문에는 이 실측으로 답이 나온다: **현재 위험 없음.**

### 2.4 팀이 할 수 없는 것

- Supabase 대시보드 Billing/Subscription 화면에서 실제 요금제 이름 확인 — 이 세션에 노출된
  MCP 도구(`get_advisors`·`get_logs`·`list_tables`·`execute_sql` 등)에는 결제 플랜 조회
  수단이 없다(037·043B가 이미 같은 결론에 도달했고, 이번에도 재확인했다 — 새 도구가 추가되지
  않았다).
- v0.2 이후 실 트래픽 기반 월간 과금 정밀 산정 — 조직적으로 실 사용자가 없어 만들 수 없는
  데이터다. 이 문서가 할 수 있는 것은 "지금 규모에서는 위험 없음"까지이고, 성장 후 재계산은
  Realtime Reports(대시보드)로 그때 가서 해야 한다(037 §6 후속과 동일).
