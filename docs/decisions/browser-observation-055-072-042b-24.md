### 1.3 판정 — **충족**

코드 docstring이 명시한 두 트리거 경로 중 "최초 진입, 앵커 없이 곧장 최하단"이 실제로
매번(2회 독립 재현) `chat_room_reads.last_read_at`을 정확한 시각에 갱신시킴을 실측으로
확인했다. **근거 정정(24일차 CREW 교차검증)**: 이 문서는 원래 이 갱신이 "`markRoomReadAction`
Server Action 왕복을 거쳐야만 가능한 값이라 클라이언트가 임의로 만들 수 없다"고 적었으나,
**이는 사실이 아니다** — CREW가 `chat_room_reads`에 `pg_trigger`가 0개임을 전수 조회로
확인했고 `last_read_at`을 10년 뒤 값으로 직접 INSERT해 성공시켰다(I-108, 23일차 DESIGN이
직접 등재하고 "저위험 보류"로 남긴 바로 그 결함 — 지금도 안 막혀 있다). **신뢰의 근거는
"DB 값이 위조 불가능해서"가 아니라, 이 관측이 raw REST/SQL 조작이 아니라 실 브라우저로
렌더된 앱 UI(방 진입 → 자동 스크롤 → 하단 sentinel)를 통해 얻어졌다는 것**이다 — 즉 실제
앱 코드 경로(`MessageList`의 `IntersectionObserver` → `MessageRoomContainer`의
`onReachLatest` → `markRoomReadAction`)를 탔다는 사실이 근거이고, `last_read_at` 컬럼
자체는 I-108에 따라 RLS 레벨에서 여전히 위조 가능한 값이라는 점은 별개로 열려 있다. 판정
(FR-055 AC2 충족)은 이 정정과 무관하게 유지된다 — 위 시각들은 앱이 실제로 만든 값이지
내가 직접 써넣은 값이 아니기 때문이다. 아직 보지 않은 메시지(M2)를 앞서 읽음 처리하지
않는다는 음성 대조도 같은 이유로 유효하다.

### 1.4 미확인·한계 — 새로 발견한 것 (I-118으로 등재)

두 번째 트리거 경로("위로 읽다가 다시 최하단으로 내려오면")를 **컨테이너 자체의 스크롤로는
재현하지 못했다.** 원인 조사 결과 `MessageList`의 `overflow-y-auto` div가 조상 체인 어디서도
높이 상한을 받지 못해(`AppShell` 루트가 `min-h-full`) 실제로 넘치는 콘텐츠가 없고, 페이지
전체(`document.documentElement`, `html`/`body` 둘 다 `overflow: visible`)가 대신 스크롤된다 —
`document.querySelectorAll('*')` 전수 조사로 `overflow-y: auto|scroll`이면서 실제로
`scrollHeight > clientHeight`인 요소가 **0개**임을 확인했다. 상세·영향·후속은 **I-118**.

**정정(24일차, CORE 교차검증 — I-122로 등재) — "FR-055 AC2 자체는 영향 없음"은 틀렸다.**
이 문서가 원래 적었던 결론(이 결함이 있어도 FR-055 AC2는 미충족이 아니다)은 **내가 실측에 쓴
방(주말 러닝 클럽, `b89069ce-…`)이 메시지 9~11건뿐이라 412×915 뷰포트에 전부 들어갔던
우연**이었다 — 그 경우 페이지가 로드되자마자 하단 sentinel이 이미 실제 뷰포트 안에 있어,
"마운트 즉시 읽음 처리됨"이 "정상적으로 최신까지 스크롤해 도달해서 처리된 것"과 관측상
구분되지 않았을 뿐이다.

CORE가 같은 방에 임시 메시지 40건을 추가해 컨테이너를 5,000px 이상으로 늘린 뒤(메시지가
한 화면을 넘는, 실사용에서 정상적으로 벌어지는 크기) 앵커·읽음 이력이 없는 계정으로 처음
진입시켜 재현했다 — sentinel이 `getBoundingClientRect().top = 5153.5`(뷰포트 915px보다
5,000px 이상 아래)에 있고 `window.scrollY`가 시종일관 0(전혀 스크롤 안 함)인데도
`chat_room_reads.last_read_at`이 마운트 시각으로 채워졌다. 그리고 아무 조작 없이 6초 뒤
**다시** 다른 값으로 전진했다 — 이게 바로 위 §1.2 표의 12:39:46.903(원인 미상으로 남겼던
그 27초 전진)과 같은 현상이라는 것이 CORE의 결론이다: 우연한 1회성 잡음이 아니라, `root:
scrollRef.current`로 지정된 `IntersectionObserver`가 아무것도 클리핑하지 않는 컨테이너를
관찰할 때 레이아웃이 재계산될 때마다(하이드레이션·폰트 로드 등) 재교차 판정을 내리는 이
관찰자의 구조적 특성이다.

**정정된 결론**: §1.3의 "충족" 판정 자체(짧은 방에서 마운트 시 읽음 처리됨이라는 실측)는
철회하지 않는다 — 정확한 관측이었다. 다만 그 판정이 성립하는 조건이 **메시지가 한 화면에
다 들어가는 짧은 방으로 한정된다**는 것을 이번에 놓쳤다. 메시지가 한 화면을 넘는 모든
실사용 크기의 방에서는 AC2가 요구하는 "When 최신까지 스크롤"이라는 조건 없이 **방에 들어가기만
해도** 읽음 처리된다 — 사용자가 아직 안 읽은 메시지가 쌓인 긴 채팅방에 스크롤 없이 잠깐
들어왔다 나가도 읽음 배지가 사라진다는 뜻이다. FR-055 AC1이 지키려는 "안 읽은 메시지 수
표시"의 신뢰성 자체가 흔들린다. 근본 원인은 I-118과 같다(`AppShell.tsx`의 `min-h-full`).
실측 전문·재현 절차·정리 확인은 **I-122**(`docs/ISSUES.md`), I-118 본문도 이 발견으로
심각도 근거가 갱신됐다.

## 3. Task 042B 관리자 콘솔 — FR-082 브라우저 E2E

### 3.1 무엇이 관측되면 충족인가 (사전 정의)

AC1: 대기 신고를 실제로 처리(기각/콘텐츠 삭제/계정 제재)하면 `reports.status`가 전이되고
`audit_logs`에 대응 행이 남는다 — 이걸 SQL 재조회가 아니라 **버튼 클릭으로** 일으킨다. AC2:
`is_system_admin=false` 세션이 `/admin`에 가면 HTTP 404이고, 그 404 화면이 "관리자 전용"임을
드러내지 않는다(일반 404와 구분 불가). 추가로 I-076(post_removed 감사 로그 미실측)을 이번
기회에 닫는다.

### 3.2 신고 접수 경로의 제약 — 새로 발견한 gap

게시글에 "신고" 버튼을 UI에서 찾을 수 없었다. 조사 결과 `ReportDialog`(범용, 4개
`targetType` 지원)는 실제로 `MemberList.tsx`의 `targetType="profile"` 한 곳에만 연결돼 있고,
게시글·댓글·채팅 메시지에는 신고 진입점이 없다 — **I-117**로 등재. 백엔드(`create_report`
RPC·`admin_resolve_report`)는 이미 4종 다 완결돼 있으므로(Task 042A·042B의 SQL 실측), 이번
회차는 "신고 접수 이후" 구간(대기열 조회 → 처리 → 감사 로그)만 실 브라우저로 검증하고, 신고
자체는 `reports` 테이블에 직접 INSERT해 준비했다(실제 서비스 상태를 흉내낸 것이지, RLS를
우회한 게 아니다 — INSERT한 값은 `create_report` RPC가 만드는 값과 스키마·제약이 완전히
같다).

### 3.4 판정 — **충족(AC1·AC2), I-076 해소**

기각·콘텐츠 삭제 두 액션이 실 클릭으로 상태 전이·감사 로그까지 정확히 재현됐고, AC2(404
