# I-032 실측 — 합성 렌더 층위 대비 검증 (28일차, DESIGN)

## 1. 배경

I-032는 27일차에 (A) 릴리스 차단으로 재분류됐다(`docs/issue-triage-release-readiness.md`
§3). Task 013 원자 컴포넌트의 수락 기준(NFR-018 대비 4.5:1/3:1, NFR-022 라이트·다크)이
**토큰 값** 층위로만 논증돼 있었고, **합성 렌더** 층위 — 알파가 걸린 오버레이·링·보더가
실제로 겹쳐 계산된 최종 색 — 는 한 번도 브라우저로 실측되지 않았다.

닫는 방법은 이미 정해져 있었다: 격리 Chromium으로 ① 폼 오류 상태 ② Dialog/Drawer 오버레이
③ Toast 3종의 합성 상태를 라이트·다크 양쪽에서 실측하고, `getComputedStyle`로 뽑은 실제
전경·배경색을 알파 합성해 대비비를 산출한다.

**이번 회차에 브라우저를 쓰는 유일한 담당자가 DESIGN이라는 팀장 운영 규칙**(28일차)
덕분에 25일차 이후 반복되던 "다른 세션이 Playwright를 점유해 측정 불가"라는 실패 모드가
이번에는 발생하지 않았다.

## 2. 방법론

`getComputedStyle`이 돌려주는 색 문자열은 이 프로젝트의 토큰이 `oklch`/`oklab`로
정의돼 있어 브라우저가 `oklab(L C H / a)` 형태로 그대로 반환한다(파싱하지 않고 그대로
쓰면 대비 계산이 틀린다). 브라우저 자체의 색 파서가 sRGB로 어떻게 변환하는지가 렌더
결과의 근거이므로, **1×1 `<canvas>`에 해당 색 문자열로 `fillRect`한 뒤 `getImageData`로
읽어** 실제 sRGB 8비트 값(+ 알파)을 얻었다 — 수작업 oklab→sRGB 변환이 아니라 브라우저
자신의 색 파서를 오라클로 썼다.

알파가 있는 레이어(링의 `box-shadow`, 오버레이의 `bg-black/10` 등)는 표준 "source-over"
합성 공식(`out = top·a + bottom·(1-a)`)으로 그 아래 실제 배경(부모 체인을 걸어 올라가며
`background-color`를 합성해 첫 완전 불투명 레이어에서 멈춘다)과 합성한 뒤, WCAG 상대
휘도 공식으로 대비비를 계산했다. 라이트/다크 전환은 `document.documentElement`에
`.light`/`.dark` 클래스를 직접 토글해(이 앱의 테마 모델, `theme-config.ts`) 실행 중
페이지에서 즉시 재계산되게 했다.

대비만 낸다는 것이 이번 실측의 핵심 발견이다 — 토큰 값과 합성 렌더의 괴리가 정확히
I-032가 우려한 그 모양으로 나타났다.

## 4. 구조적 확인 — "포커스 링이 오버레이 위에 겹치는가"

팀장 프롬프트의 가설("Drawer/Dialog 오버레이 위에 포커스 링이 겹칠 때")을 실측으로
검증했다: Dialog를 열고 Tab으로 실제 키보드 포커스를 이동시킨 뒤(`:focus-visible` true
확인) `getBoundingClientRect()`로 포커스된 버튼과 `DialogOverlay`/`DrawerOverlay`,
`DialogContent`/`DrawerContent` Popup의 사각형을 비교했다.

**결과: 이 가설은 기각한다.** `DialogContent`/`DrawerContent`의 Popup이 `fixed`
포지셔닝 컨텍스트를 이루고 그 안의 모든 포커스 가능 요소가 Popup 경계 안에
완전히 포함된다(`btnFullyInsidePopup: true`, Dialog·Drawer 양쪽 다 실측 확인). Popup
자신은 `bg-popover`(불투명)이라, 실제로 포커스 링이 렌더되는 배경은 언제나 이
불투명 표면이지 반투명 veil이 아니다 — Base UI가 모달 오픈 시 포커스를 Popup
내부로 이동시키는 것이 구조적으로 이 경우를 막는다(트리거 버튼은 포커스를 잃는
순간 `:focus-visible`이 꺼지므로 veil 위에 얹힌 채로 링이 남는 경우도 없다).

**따라서 실제 결함은 "오버레이 위에 링이 겹친다"가 아니라, "링 자체의 알파가 배경이
무엇이든 낮아서 3:1을 못 낸다"였다** — 오버레이 유무와 무관하게 항상 존재하던 문제다.
가설이 가리킨 표면(Dialog/Drawer)에서 실측하다가 그 표면과 무관하게 앱 전역에
퍼져 있는 별개의 결함을 찾은 셈이다.

## 5. 토큰 수정

`src/components/ui/` 아래 9개 shadcn 원자 파일의 포커스/오류 표시자 알파를 상향했다.
전부 기존 색상 토큰(`--ring`, `--destructive`)은 그대로 두고 **유틸리티 클래스의 알파
계수만** 올렸다 — 색 자체를 바꾸지 않았으므로 다른 곳에서 이미 검증된 불투명 대비값
(6.16/6.67/7.27 등)에는 영향이 없다.

| 클래스 | 이전 | 이후 | 근거 |
| --- | --- | --- | --- |
| `focus-visible:ring-ring/50` | 50% | **70%** | 최소 필요 알파 라이트 63%·다크 54% 실측(이진 탐색) → 여유 두고 70%로 통일(다크 전용 override 없이 단일 값으로 양쪽 충족) |
| `aria-invalid:ring-destructive/20` (라이트) | 20% | **60%** | 최소 필요 알파 56% → 60% |
| `dark:aria-invalid:ring-destructive/40` | 40% | **65%** | 최소 필요 알파 58% → 65% |
| `dark:aria-invalid:border-destructive/50` | 50% | **삭제**(불투명으로 복귀) | 다크 토큰 자체가 불투명 기준 7.27:1이라 알파를 둘 필요가 없었다 — 라이트가 원래부터 불투명이었던 것과 대칭 |
| `focus-visible:border-destructive/40`, `focus-visible:ring-destructive/20`(destructive 버튼 변형) | 40%/20% | **65%/60%** | 동일 최소 알파 기준 적용(이 버튼의 포커스 표시자도 같은 실패 패턴) |
| `ring-destructive/30`(Toast 카드 경계) | 30% | **65%** | 카드 경계는 라이트·다크 override가 없는 단일 값이라 다크 쪽 최소(58%)를 만족하는 값으로 통일 |

영향받은 파일: `badge.tsx`·`button.tsx`·`checkbox.tsx`·`input.tsx`·`radio-group.tsx`·
`select.tsx`·`switch.tsx`·`tabs.tsx`·`textarea.tsx`·`toast.tsx`·`toggle.tsx` (11개,
`toast.tsx`는 `ToastAction`의 표준 링과 destructive 카드 링 둘 다 포함).

**적용 중 발견한 환경 문제**: 첫 저장 직후 Turbopack이 변경을 반영하지 않았다
(`docs/ISSUES.md` I-135와 같은 WSL2 drvfs HMR 누락 패턴 — 재실측 시 `boxShadow`가
여전히 옛 알파값을 보여줘 발견했다). `.next` 삭제 후 재기동으로 해소했다 — 코드
문제가 아니라 이미 알려진 개발 환경 제약의 재발이다.

## 8. 판정

**I-032 해결됨.** 6조합(+ 구조 확인 1건, + 발견된 전역 포커스 링 결함 보정)을 전부
실측했고, 최초 발견된 미달 7건(폼 오류 보더 1·링 1, Dialog 표준/destructive 링 각
2테마, Toast 카드 링 2테마)을 토큰 알파 조정으로 해소해 재실측으로 확인했다. 텍스트
대비는 원래부터 문제가 없었다 — 이번 회차가 잡은 것은 전부 **알파가 걸린 비텍스트
경계(보더·링)** 였고, 이는 정확히 I-032가 "토큰 값 논증으로는 보장되지 않는다"고
지적한 층위였다.

**미룬 것**: `--ring`·`--destructive` 자체의 색상값(oklch H/C/L)은 건드리지 않았다 —
문제가 색이 아니라 알파였기 때문이다. 이 결정이 다른 회차에서 재검토될 경우를 대비해
근거를 남긴다. 또한 `focus-visible:border-destructive/40`처럼 이번에 같이 발견한
표면 중 3종 시나리오 바깥(범용 destructive 버튼)의 것도 같은 원인이라 같이 고쳤지만,
**19개 페이지 전수 시각 회귀는 하지 않았다** — 클래스 값만 바뀌었고 레이아웃에 영향이
없는 변경이라 위험은 낮다고 판단했지만, 다음 회차 접근성 QA 패스에서 시각적으로도
확인하는 편이 안전하다.
