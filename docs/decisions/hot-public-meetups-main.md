# 메인 "지금 활발한 모임" — Meetup 공개 노출 경계 확장 (D-109)

**작성**: 팀장 (2026-07-31, 36일차 이후 사용자 요청 대응)
**상태**: 확정·적용 완료 (마이그레이션 `20260731062658`)

---

## 0. 왜 이 문서가 필요한가 — 기존 결정을 뒤집기 때문이다

사용자 요청은 "메인에 실시간 핫한 모임 5개"였고, 확인 결과 **랜딩(비로그인) + 홈 양쪽에,
공개 크루 전체를 대상으로, 최근 활동량 순으로** 보여 달라는 것이었다.

그런데 이 프로젝트에는 정반대 방향의 결정이 이미 문서화돼 있었다. `meetup_directory_summary`
(`supabase/migrations/20260725141946_meetup_directory_summary_i073.sql`, I-073/D-048) 본문:

> 크루(D-007)와 달리 Meetup에는 독자적인 공개 범위 개념이 없다 — 접근 게이트는 오직
> "크루원인가"뿐이고 **게스트(비로그인) 노출은 애초에 설계돼 있지 않다**(meetups RLS 전체가
> authenticated 크루원 전용). … **회의·날짜·장소 등 실제 콘텐츠는 절대 이 경로로 노출되지
> 않는다.** … **anon에게는 노출하지 않는다** — meetups는 처음부터 인증 크루원 전용이라 게스트
> 접근 시나리오 자체가 없다.

실제 RLS도 그렇다 — `meetups_select_members`는 `crew_id IN (내 활성 멤버십)` 하나뿐이라
**크루 경계를 넘는 목록은 원리적으로 조회되지 않는다.**

따라서 이 요청은 "화면 하나 추가"가 아니라 **노출 정책 변경**이다. 사용자에게 이 충돌을
명시적으로 알리고 진행했다. 이 문서가 그 변경의 기록이다.

## 1. 무엇이 바뀌었나

D-048은 **여전히 유효하다** — 그 결정이 다루는 것은 `getMeetupById`의 404→403 폴백 경로이고,
그 경로는 지금도 `crewId` 두 값만 돌려주며 `anon`에게 닫혀 있다. 바뀐 것은 **새 통로가 하나
생겼다**는 것이다:

| | `meetup_directory_summary` (D-048) | `hot_public_meetups` (D-109, 신규) |
| --- | --- | --- |
| 목적 | 비소속자에게 정확한 `forbidden` 분기를 주기 위한 존재 확인 | 공개 크루의 활발한 모임 소개 |
| 대상 | 모든 Meetup(크루 공개 여부 무관) | **공개·활성 크루의 예정된 확정 모임만** |
| 반환 | `id`, `crew_id` **둘뿐** | 제목·날짜·시각·참석 인원·정원 + 크루 이름·카테고리·색 |
| `anon` | **불가** | **가능**(랜딩이 게스트용이라 필수) |

## 2. 노출 경계 — 무엇을 내보내고 무엇을 감추는가

**필터(전부 RPC 본문이 강제한다. 앱 레이어는 아무것도 거르지 않는다.)**

- `crews.visibility = 'public'` **AND** `crews.status = 'active'` — private 크루는 D-017대로
  한 건도 나오지 않고, 해산 크루도 빠진다.
- `meetups.status = 'confirmed'` **AND** `meetups.date >= current_date` — 취소된 모임과 지난
  모임은 나오지 않는다.
- 크루당 1건.

**내보내는 것**: 모임 제목·날짜·시작 시각·참석 인원·정원, 크루 이름·카테고리·색 키.

**의도적으로 내보내지 않는 것**

- **`meetups.place`** — 가장 중요한 제외다. 불특정 다수(비로그인 포함)에게 오프라인 집결지를
  공개하는 것은 데이터 노출과는 **다른 차원의 위험**이고, 이 화면의 목적(어떤 모임이 활발한지
  보여주기)에 필요하지도 않다. 장소는 크루에 들어가야 보인다.
- **`meetups.description`** — 본문은 크루원 대상으로 쓰인 글이다. 제목만으로 목록의 목적은
  충족된다.
- **원시 활동량**(게시글·투표·채팅 각각의 건수) — `activity_score`는 `3·게시글 + 2·투표 +
  1·채팅` 가중 합성값이라 개별 카운트로 역산되지 않는다.

`HotMeetup` 타입에 `place`·`description` 필드를 **아예 두지 않은 것**도 같은 이유다 —
`Meetup`을 재사용해 `null`로 채우면 "장소가 없는 모임"과 "노출이 금지돼 비운 것"이 타입에서
구분되지 않아, 나중에 누가 데이터 결손으로 오해하고 채워 넣을 수 있다.

## 3. "핫함"의 정의

**최근 7일** 동안 그 크루에서 일어난 활동의 가중 합:

| 활동 | 가중치 | 출처 |
| --- | --- | --- |
| 게시글 | 3 | `posts`(소프트삭제 제외) |
| 투표 | 2 | `poll_votes`(`invalidated = false`) |
| 채팅 | 1 | `chat_messages`(소프트삭제 제외) |

가중치를 둔 이유: 채팅은 다른 둘보다 자연히 수십 배 많아 그대로 합치면 **채팅량 랭킹**이 된다.
게시글은 한 건당 의도와 노력이 가장 크므로 가장 높게 쳤다.

**점수는 크루 단위이고 모임 단위가 아니다.** 사용자가 요청한 지표(게시글·투표·채팅)가 전부
크루 활동이기 때문이다 — 모임 자체에는 그런 활동이 붙지 않는다.

### 3.1 크루당 1건 제한은 실측이 만든 결정이다

첫 시안에는 이 제한이 없었다. 실행하니 **5칸이 전부 같은 크루("알고리즘 스터디")로 채워졌다** —
점수가 크루 단위라 활발한 크루 하나가 자기 예정 모임 5건으로 목록을 독점한다. "핫한 모임 5개"의
취지가 그대로 깨진다. `row_number()`로 크루마다 가장 임박한 1건만 남기고 크루 점수 순으로
고르도록 고쳤다(적용 후 재실측: 서로 다른 5개 크루).

**이 결함은 SQL을 읽어서는 눈에 띄지 않았고 실행해서만 드러났다.** 랭킹 쿼리를 새로 쓸 때는
반드시 실제 데이터로 한 번 돌려 본다.

### 3.2 정렬은 완전 결정적이다

`activity_score desc, attending_count desc, meetup_date asc, id asc` — 마지막 `id`가
타이브레이커다. 35일차 판정 기준("ORDER BY 없는 목록은 순서를 보장하지 않는다")을 따랐다.

## 4. "실시간"의 범위 — 요청 시 최신

서버 컴포넌트로 조회한다(화면 진입·새로고침 시 최신). **Realtime 구독을 넣지 않았다** — D-030
②가 요구하는 구독 인터페이스 + 클라이언트 컴포넌트 + 상태 소유권 이동이 따라오는데, 이 섹션은
랜딩·홈처럼 오래 열어 두지 않는 화면의 부차적 소개 영역이라 그 비용이 정당화되지 않는다.
사용자에게 이 선택지를 명시해 확인받았다.

## 5. 시각 설계 — 활동 잔물결

순위 숫자를 크게 박는 흔한 처리 대신, 각 행 아래 **크루 색으로 번지는 얇은 막대**의 폭으로
1위 대비 상대 활동량을 표현한다.

**이유**: 순위는 순서만 알려주고 **격차를 알려주지 않는다.** 이 목록에서 실제로 궁금한 것은
"1위가 압도적인지, 다섯이 비슷한지"다. 종이에 잉크가 번진 정도라는 비유는 기존 표면
(`surface-warm`·certainty 스케일)과 같은 재료를 쓴다.

- **새 색·새 폰트를 만들지 않았다** — 크루 12색 팔레트(D-026)와 이미 로드된 Geist Mono(순위
  숫자 = 데이터라 유틸리티 페이스)만 쓴다.
- **막대는 보조 신호다**(`aria-hidden`). 순서 정보는 순위 텍스트가 전달한다 — 색·폭만으로
  정보를 전달하지 않는다(WCAG 1.4.1, D-026과 같은 원칙).
- **certainty 스케일을 쓰지 않았다** — 이 목록은 `confirmed` 모임만 담아 확정성이 변수가
  아니라 상수다. 그 축으로는 아무것도 구분되지 않는다.
- **애니메이션을 넣지 않았다** — 과감함은 잔물결 하나로 충분하다.

## 6. 잔여 위험 (정직하게 남긴다)

1. **상대 비율은 노출된다.** `intensity`는 1위 대비 비율이라 "2위는 1위의 72%"를 읽을 수 있다.
   어떤 랭킹 표시에도 내재하는 정보라 추가 노출로 보지 않았지만, 절대량이 아니라는 점을 기록한다.
2. **제목은 자유 텍스트다.** 사용자가 제목에 장소를 적으면(`"강남역 러닝"`) `place`를 감춘 의미가
   약해진다. 다만 공개 크루의 `name`·`description`은 `crew_directory_summary`로 이미 `anon`에게
   열려 있어(D-007) 새로 생긴 종류의 위험은 아니다. **재검토 조건**: 제목에 장소를 적는 관행이
   실제로 관측되면 이 결정을 다시 연다.
3. **활동량 지표는 어뷰징에 열려 있다.** 채팅을 반복 전송하면 점수가 오른다. 지금은 노출이
   목록 5칸뿐이고 금전적 유인이 없어 방치한다 — **재검토 조건**: 이 목록이 크루 성장에 실제로
   기여하기 시작하면(유입 지표로 확인되면) 레이트 리밋 또는 고유 작성자 수 기반으로 바꾼다.
4. **점수 계산이 매 요청마다 전 공개 크루를 훑는다.** 크루 42개 기준으로는 문제가 없지만
   선형으로 늘어난다. **재검토 조건**: 공개 크루가 수백 개가 되면 집계 테이블이나 캐시로 옮긴다.

## 7. 검증 결과 (전부 실측)

| 항목 | 결과 |
| --- | --- |
| `anon`(게스트) 호출 | 5건 반환 |
| `authenticated` 호출 | 5건 반환 |
| private·해산 크루 유출 | **0건** |

측정 방법 메모: 처음에는 `DO` 블록 안에서 `set_config('role', …)`로 역할을 바꿔 측정했는데
`anon`·`authenticated` 둘 다 `42501`이 나왔다. **이건 가짜 음성이었다** — `DO` 블록 안의
`set_config`는 바깥 함수 호출의 권한 판정에 반영되지 않는다. `set local role`로 다시 재면 둘 다
정상 동작한다. **역할별 권한을 잴 때는 `set local role`을 쓴다.**
