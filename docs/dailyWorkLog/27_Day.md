  아래에 세그먼트가 하나 더 있는 형태만 골라 깨진다"는 패턴 관찰까지 좁혔다.

## 설계 판단 — handle 해석을 앱이 아니라 DB에 둔 이유

이번 회차에서 **3단 검증이 온전히 작동한 유일한 사슬**이다.

1. **DESIGN이 멈춰서 물었다.** `admin_grant_system_admin(p_profile_id uuid)`는 UUID가 필요한데
   `profile_search`(NFR-013 3필드 계약)는 의도적으로 `id`를 주지 않는다. DESIGN의 원안은 앱
   레이어에서 `getProfileByHandle`(service-role, RLS 완전 우회)로 해석하고 `eslint.config.mjs`의
   허용 목록에 3번째 파일을 추가하는 것이었고, **진행하기 전에 팀장에게 확인을 요청했다.**
2. **팀장이 기각했다.** 그 방향은 Server Action 안에서 `①handle 해석 → ②forbidden 검사` 순서가
   되어, 비관리자가 권한 거부를 받기 **전에** 사용자 존재를 알아낸다 — R-012이고 **I-074가 두 번
   실제로 뚫린 자리**다. 결정적인 이유는 I-074의 결론이 **"문서 규약은 컴파일러가 강제하지
   않는다"**였다는 것 — 그 자리를 다시 "순서를 잘 지키면 안전하다"는 규약으로 막는 것은 같은
   실수의 반복이고, 허용 목록이 늘어나는 순간 규칙의 억지력 자체가 약해진다.
3. **CORE가 구현하고 팀장이 실측했다.** handle 해석을 SECURITY DEFINER RPC 안에 두어 권한 검사가
   **구조적으로** 먼저 실행되게 했다. 팀장 검증 결과:

| 호출자 | handle | ok | reason_code |
| --- | --- | --- | --- |
| 비관리자 | **존재함** | false | `forbidden` |
| 비관리자 | **없음** | false | **`forbidden`** (응답 동일 → 열거 불가) |
| 관리자 | 없음 | false | `handle_not_found` |
| 관리자 | 자기 자신 | false | `cannot_target_self` |

`anon`은 EXECUTE가 없어 직접 호출 시 `42501`이다(CORE가 ACL 조회로 끝내지 않고 실제 `anon` 롤로
호출해 재현했다).

## 팀원이 팀장을 정정한 3건 (CREW)

| 항목 | 팀장 보고 | CREW 정정 |
| --- | --- | --- |
| 트리거 수 | "30→30, 26일차의 34와 기준이 다르니 비교 말라" | **원인 규명**: `pg_trigger`는 트리거 오브젝트당 1행(다중이벤트는 비트마스크로 압축), `information_schema.triggers`는 이벤트별로 펼침. 다중이벤트 트리거 4개 × 추가 1행 = 30+4=34. **26일차부터의 혼선이 끝났다**(§10.2에 문서화) |
| 함수 델타 | "public +3" | **private도 +3, 총 +6** — 029B 2단 구조라 겉보기 RPC 3개가 실제 오브젝트 6개를 만든다 |
| 마이그레이션 | "3건" | **4건** — 팀장 통지 후 CORE가 하나 더 적용한 것을 원문 대조로 발견 |

세 건 다 팀장이 "내 숫자에 맞추지 말고 독립 측정하라"고 지시한 결과다. 맞췄다면 트리거 혼선은
다음 회차로 넘어갔고, 함수 델타는 절반만 설명된 채 "설명됨"으로 기록됐을 것이다.

**팀장의 판단 오류도 하나 있었다** — "BOARD 마이그레이션에는 D-\* 번호가 없어 옮기기 싸다"고
판단했으나, 그것은 `grep`을 로컬 파일에 돌렸고 **그 파일이 아예 없어서 빈 결과가 나온 것을
"번호 없음"으로 오독**한 결과였다. CREW가 `schema_migrations.statements`(원격 원문)를 직접 읽어
잡아냈다.

## 교차검증 결과

리뷰 짝 배정은 프로필의 `리뷰 짝` 행을 따랐으나, 26일차와 같이 **팀원 간 상호 검증 루프가

  "관례 A도 이미 안전"(`chat_messages_guard_delete_only()`를 `authenticated`로 호출 →
  `0A000 trigger functions can only be called as triggers`). 재현됐으므로 **소급하지 않은
  결정이 근거를 갖는다**(관례 A가 실제로 뚫려 있었다면 11개를 방치하는 판단이 됐을 것이다).
- **팀장 → CORE(I-075)**: **PASS.** 자기반증 6단계를 독립 재현해 전부 일치. 처음에 예외 기반으로
  테스트해 전부 "NO ERROR"가 나왔는데, 함수가 `returns table(ok, reason_code)`로 **반환값으로
  실패를 알리는 설계**여서 팀장의 방법이 틀린 것이었다. 특히 **같은 호출(자기 자신 회수)이
  관리자 수에 따라 다른 사유로 걸리는 것**(1명 → `last_admin_forbidden`, 2명 → `cannot_target_self`)

  - **추가 검증**: CORE의 §5 논리("정상 경로에서 트리거 조건이 성립하지 않는다")만으로는
    **트리거가 여전히 살아 있는지** 증명되지 않아 팀장이 직접 확인했다 — 비관리자 자가 승격은
    `P0001` 거부, 관리자의 raw UPDATE 우회는 `row_count=0`. 새 RPC가 생긴 뒤에도 D-049의
    자가 승격 차단이 유지된다. **이 검증 중 I-137(D-048 오참조)을 발견했다.**
  - 그랜티: `private` 4종이 기존 DEFINER 함수 17개와 동일 패턴, `public` 4종은 `anon` 없음.
- **팀장 → BOARD(I-130)**: **PASS.** 자기반증 핵심 3항목 독립 재현 — 첫 제안 통과 / 두 번째
  `P0001` 거부(메시지에 `I-130`·`target_meetup_id` 포함) / 일반 FR-034 제안 통과(회귀 없음).

  `/admin`이 HTTP 200에 헤딩 `관리자 콘솔`·`신고 관리`·**`시스템 관리자`**와 버튼 **`관리자 지정`**·
  **`회수`**를 렌더하고 콘솔 오류 0, `/sample`에 `SystemAdminList` 등록 확인. **비관리자 세션은
