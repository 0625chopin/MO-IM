## 0. 결론 (36일차 실측 반영 최종판)

**최초 판정(문서 대조만으로 낸 판정)과 실측 후 판정이 다르다 — 아래는 실측을 반영해 다시 쓴
결론이다.** 최초 판정 과정은 §1·§2에 그대로 남기고 무엇이 왜 바뀌었는지 병기했다(append-only
관행).

1. **실측으로 셋 중 하나만 확정 결함으로 남았다.** 팀장이 §4 프로토콜(실험 A·B)로 I-048의
   재현 조건 ①(동시 dev+build)·②(abrupt kill 후 재시작)를 각각 독립 실행했고 **둘 다 재현
   안 됨**(SST/Compaction 에러 0건, `routes-manifest.json` 정상 생성, `.next/dev`가 `.next`와
   분리된 디렉터리로 실제 존재 확인 — §3.3에서 예측한 Next 16의 "동시 dev+build" 수정이 실물로
   확인됐다). 반면 실험 C(I-135)는 **처음으로 의도적으로 재현됐고**(팀 관찰 사상 5번째, 첫
   의도적 재현), 재시작만으로 해소돼 팀이 정한 구분 기준대로 **I-135로 확정 귀속**됐다. 팀장이
   확장한 실험 D·F는 I-135의 원인을 **drvfs(정확히는 `v9fs`, 9P 프로토콜 마운트, §7) 그 자체**로
   대조군까지 갖춰 확정했다 — Turbopack의 특정 캐시 기능도, 편집 방식(inode 교체 여부)도
   원인이 아니다(§1 I-135 절 "36일차 팀장 실측 갱신" 참고).
2. **"클러스터"로 묶어 부르는 것의 근거가 약해졌다 — 유지하되 성격을 다시 정의해야 한다.**
   최초 판정(아래 원문 유지)은 "트리거 계열이 같다"(drvfs 위치·Turbopack·`.next` 공유)는
   근거로 셋을 느슨하게 묶었다. 그런데 I-048의 재현 조건 둘 다 이 버전(16.2.11)에서 재현되지
   않는다는 것은, 그 "같은 트리거 계열"이라는 전제 자체가 **적어도 I-048에 대해서는 더 이상
   유효하지 않을 수 있다**는 뜻이다. 지금 시점 판정: **I-135만 이 회차 기준 확정 재현된
   결함**이고, I-048·I-139는 "과거 관찰 기록은 있으나 이 버전·이번 실험 조건에서는 재현되지
   않는(I-048) 또는 여전히 미실험 상태인(I-139) 이슈"로 성격이 갈렸다. 세 이슈를 계속 하나의
   "클러스터"라는 우산으로 부르면 **I-135의 확정된 원인(drvfs 파일 워처)을 I-048·I-139에도
   있을 것처럼 오해하게 만들 위험**이 있다 — I-083·I-087 선례("트리거는 같지만 메커니즘은
   다르다")보다 한 걸음 더 나아가, 이번엔 트리거 계열 공통성 자체도 실측으로 약화됐다.
3. **완화책의 조준점이 틀렸었다.** §5(원안)가 제안한 "`turbopackFileSystemCacheForDev: false`"는
   온디스크 컴파일 캐시 축을 겨냥한 것인데, 실측으로 확정된 결함(I-135)은 **파일 워처 축**이다
   — 캐시를 꺼도 I-135는 전혀 해소되지 않는다(캐시와 워처는 다른 Turbopack 서브시스템이라는
   원래 분석은 맞았지만, 그 분석이 겨냥한 축 자체가 재현되지 않는 축이었다). 팀장이 추가로
   실측한 완화책 후보(`watchOptions.pollIntervalMs`)도 **효과 없음 + 부작용(watch error
   11건)**으로 확인됐다(§5 개정판, 실험 E). **실측으로 유일하게 효과가 확인된 것은 "네이티브
   파일시스템으로 옮기기"뿐**이다(실험 F 대조군).
4. **여전히 미확정인 것**: I-048·I-139 자체가 "결함이 없다"고 확정된 것은 아니다 — 이번에
   재현을 시도한 조건(①동시 dev+build, ②abrupt kill)에서만 재현되지 않았을 뿐, I-048의 조건
   ③("단일 프로세스 상태에서도 드물게 자연 발생")과 I-139(5회 관찰, 재현 조건 자체가 애초에
   미확보)는 이번 실측 대상이 아니었다. WSL2 drvfs가 inotify를 안정적으로 전달하지 못한다는
   일반 지식은 이번 실측(실험 D·F)으로 **이 프로젝트의 실제 재현 조건과 부합함이 처음으로
   직접 확인**됐다(§3.5 갱신) — 다만 그 근거로 쓴 외부 GitHub 이슈(#4739)가 정확히 같은
   메커니즘을 설명하는지는 여전히 미검증이다(§6).

### 0.1 최초 판정 원문 (34일차 문서 대조 시점, 실측 전 — 참고용으로 보존)

> 1. 세 이슈는 "하나의 현상"이 아니라 최소 두 갈래의 메커니즘이다. I-135(파일 워처/HMR 누락)는
>    재시작만으로 해소되는 반면, I-048·I-139는 재시작으로 안 풀리고 `.next` 삭제가 필요하다 —
>    이건 팀이 이미 I-135 블록(`docs/ISSUES.md:6343`)에 스스로 적어 둔 유일한 구분 기준이다.
>    이 구분 기준을 그대로 적용하면 I-048·I-139가 한 계열(온디스크 캐시 손상), I-135가 다른
>    계열(파일 워처 누락)로 갈린다.
> 2. "클러스터"로 묶어 부르는 것은 정당하되, "같은 결함"이라고 부르면 안 된다. 셋 다 ① 이
>    저장소가 `/mnt/e`(WSL2 drvfs)에 있다는 사실 ② Turbopack(`next dev`/`next build`) ③ 여러
>    세션이 `.next`를 공유한다는 조건을 공통 트리거 계열로 갖는다 — I-083·I-087 선례("트리거는
>    같지만 메커니즘은 다르다")와 정확히 같은 패턴이다.
> 3. 문서로 확인한 것: (a) 이 Next.js 버전(16.2.11)은 `next dev`의 Turbopack 파일시스템 캐시가
>    기본값 켜짐이다 — I-048의 "영속 캐시를 끄는" 완화책 후보는 실존하는 설정이다. (b)
>    `distDir`은 프로젝트 디렉터리를 벗어날 수 없다 — "캐시 디렉터리를 WSL 네이티브 경로로
>    이동"은 존재하지 않는 옵션이다. (c) Next 16은 동시 dev+build를 지원한다고 명시한다 —
>    I-048의 재현 조건 ①이 이미 고쳐졌을 가능성이 있다. 재현 실험 최우선 항목.
> 4. 여전히 미확정인 것: 세 이슈 모두 정확한 유발 조건은 확보되지 않았다. WSL2 drvfs가
>    inotify 이벤트를 안정적으로 전달하지 못한다는 것은 일반적으로 알려진 제약이지만, Next.js
>    공식 문서 어디에도 이 내용이 없고, 이 프로젝트의 파일 편집 조건과 정확히 일치하는지도
>    미확정이다.

**이 절이 위 §0.1과 다시 갈리는 지점**: 3번(문서 확인 사실)은 여전히 유효하다 — 캐시 옵션이
실존한다는 것, `distDir` 이동이 불가능하다는 것, Next 16의 동시 dev+build 지원 서술 모두
문서적으로는 그대로 맞다. **바뀐 것은 "그 문서적 사실이 실제로 어느 이슈를 설명하는가"다** —
동시 dev+build 지원은 실측으로 확인됐지만(실험 A) 그게 설명하는 I-048 자체가 재현되지 않았고,
캐시 옵션은 실존하지만 I-135(유일하게 재현된 결함)와는 무관한 축이었다.

## 1. 세 이슈 정독 요약

### I-048 · Turbopack 영속 캐시가 `/mnt/e`에서 불안정 (`docs/ISSUES.md:1014`)

- **상태**: 열림. 제보 CREW, 17일차, Task 030 실측 중 **3회 재현**.
- **증상**: `Persisting failed: Unable to write SST file … / Compaction failed: Another write
  batch or compaction is already active` 에러 → `routes-manifest.json` 등 필수 산출물이 아예
  생성되지 않음 → **모든 라우트가 500**.
- **재현 조건(원문 그대로)**: ① 같은 저장소에서 `next dev`와 `next build`를 동시 실행 ②
  정상 종료 안 된 프로세스를 `kill` 후 재시작 ③ 단일 프로세스에서도 드물게 자연 발생(원인
  미확정).
- **해소법**: `rm -rf .next` 후 재시작 — **매번** 복구된다(원문 표현).
- **핵심 특징**: 셋 중 유일하게 **구체적인 에러 메시지**(SST/Compaction, RocksDB류 LSM-tree
  저장 엔진의 전형적 오류 문자열)를 갖고 있어 원인 계열을 좁힐 수 있는 유일한 이슈다.
- **36일차 팀장 실측 갱신 — 조건 ①·② 둘 다 재현 안 됨.**
  - **실험 A(조건 ①, 동시 dev+build)**: `.next` 클린 → `npm run dev` 백그라운드(`/tmp/
    i048-dev.log`, `✓ Ready in 3.4s` 확인) → dev가 뜬 채로 `npm run build` 실행 → **build
    exit 0**, `Persisting failed|Compaction failed|SST file` 매치 **0건**,
    `.next/routes-manifest.json` 정상 생성, build 이후에도 dev가 `/sample`·`/` 둘 다 200
    (`/tmp/i048-dev.log`: `GET /sample 200 in 17.6s`, `GET / 200 in 1596ms`). **`.next/dev`
    디렉터리가 `.next/`와 별도로 실제 존재함을 확인** — §3.3에서 문서로 예측한 "별도 출력
    디렉터리" 기제의 실물 증거다.
  - **실험 B(조건 ②, abrupt kill → 재시작)**: 워밍업으로 `/sample`·`/login`을 컴파일시켜 캐시를
    실제로 쓰게 한 뒤(`/tmp/i048b-1.log`) `kill -9` → 재기동(`/tmp/i048b-2.log`: `✓ Ready in
    4.2s`) → SST/Compaction 매치 0건, `GET /sample 200 in 8.9s`로 정상 응답.
  - **판정**: I-048의 재현 조건 ①·②는 **이 버전(16.2.11)에서 관측되지 않는다.** 조건
    ③("단일 프로세스에서도 드물게 자연 발생")은 결정론적 실험을 설계할 수 없어 이번에도
    시험하지 못했다 — I-048이 "해결됨"으로 확정된 것이 아니라 **이번 실측 범위 밖으로만
    남는다.**

### I-135 · Turbopack HMR이 WSL2 drvfs에서 소스 변경을 놓친다 (`docs/ISSUES.md:6322`)

- **상태**: 열림 — **4회 관찰**(29일차 CREW 1회 + DESIGN 1회, 30일차 CREW 1회 + DESIGN 1회).
- **증상**: 파일을 저장했는데 이미 떠 있는 `next dev` 세션이 재컴파일 흔적 없이 옛 내용을 계속
  서빙. 에러는 없음(200을 계속 반환) — 단지 **내용이 갱신되지 않을 뿐**.
- **재현 조건**: 확정 안 됨(1회 관찰). 다만 **팀 스스로 정한 구분 절차**가 있다 — "`.next`를
  바로 지우지 말고 프로세스 재시작만 먼저 시도한다. 그걸로 풀리면 I-135, 안 풀리면 I-139다"
  (`docs/ISSUES.md:6342-6345`).
- **해소법**: **프로세스 재시작만으로 해소**(`.next` 삭제 불필요) — 4회 관찰 중 2회(29일차,
  30일차 DESIGN)가 이 경로로 확정 귀속됐다. 나머지 2회(28일차·30일차 CREW)는 재시작만 단독
  시험을 안 해서 I-135/I-139 어느 쪽인지 미확정으로 남아 있다.
- **핵심 특징**: 크래시가 없다. 컴파일 로그 자체에 재컴파일 시도가 잡히지 않는다 — 이건
  "캐시가 깨져서 잘못된 결과를 서빙"하는 것과 다르다, **애초에 변경 이벤트를 못 받아 재컴파일을
  시도조차 안 한 것**으로 읽힌다(파일 워처 누락 가설과 일치).
- **36일차 팀장 실측 갱신 — 100% 재현, 5번째 관찰이자 첫 의도적 재현, 원인을 대조군으로 확정.**
  - **실험 C(판별 절차 실행)**: 편집 후 5초 대기에도 `curl`의 `<h1>`이 그대로였고, dev 로그
    (`/tmp/i135-dev.log`)에 두 번째 `GET /sample`(`689ms`)에서도 "○ Compiling" 라인이 다시
    찍히지 않았다 — 최초 로드 때 단 한 번(`○ Compiling /sample ...`)만 있고 이후 재컴파일
    시도 자체가 로그에 없다. `.next`를 지우지 않고 프로세스만 재시작(`/tmp/i135-dev-2.log`,
    새 프로세스라 "○ Compiling"이 다시 찍힘)하자 **반영됨** → 팀이 정한 구분 기준대로
    **I-135로 확정 귀속**(`.next` 삭제 단계 `/tmp/i139-dev-3.log`는 생성되지 않았다 — 재시작
    단계에서 이미 해소돼 그 다음 분기로 갈 필요가 없었다).
  - **실험 D(팀장 확장 — 편집 방식이 변수인가, "`sed -i`가 inode를 교체해 워처가 놓친다"는
    가설 시험)**: 제자리 쓰기(python `open('w')`+`fsync`, inode 유지 확인 —
    `27584547718228090` 동일)와 `sed -i`(inode `27866022694938746`→`27303072741517492`로
    교체) 두 방식을 대조했다. **둘 다 누락** — `/tmp/expD-dev.log`는 최초 1회
    `○ Compiling /sample ...` 이후 8회 연속 `GET /sample`에서도 재컴파일 로그가 전혀 없다.
    **가설 기각**: 편집 방식(inode 교체 여부)은 변수가 아니다 — 이 구성에서는 편집 방식과
    무관하게 100% 누락된다.
  - **실험 E(팀장 확장 — 완화책 실측, §5로 이관)**: `watchOptions.pollIntervalMs`를 시험했으나
    효과 없음 + 부작용 확인. 상세는 §5.
  - **실험 F(팀장 확장 — drvfs 대조군, 이 이슈의 원인을 확정한 실험)**: 저장소를 `node_modules`째
    WSL 네이티브 경로(`/home`)로 복사해 같은 Next 버전·같은 `sed -i` 편집·같은 8초 대기로
    대조 시험했다. `/mnt/e`(`stat -f` 리포트: `v9fs`)에서는 누락·재컴파일 없음(기존과 동일),
    `/home`(`ext2/ext3`)에서는 **`✓ Compiled in 36ms`로 즉시 반영, watch error 0건**
    (`/tmp/expF-dev.log`). 파일시스템 외 모든 변수(Next 버전·편집 방식·대기 시간)를 고정했으므로
    **I-135의 원인은 Turbopack 자체도, 편집 방식도, 영속 캐시도 아니라 마운트 파일시스템
    (v9fs/drvfs)이다** — 이 프로젝트가 4회 관찰 내내 가정만 하고 한 번도 두지 않았던 대조군을
    이번에 처음 확보했다. 대조군 디렉터리는 실험 후 삭제됨.
  - **판정**: I-135는 **확정 결함**이다. 원인은 편집 방식·Turbopack 특정 기능이 아니라
    **드라이브 마운트 자체**(§7 용어 노트 참고)이고, 이 구성에서는 간헐적이 아니라 **100%
    재현**된다.

### I-139 · 공유 dev 서버의 `.next` 캐시 오염 (`docs/ISSUES.md:6556`)

- **상태**: 열림 — 완화 절차만 문서화, 유발 조건 미확보. **5회 관찰**(BOARD 3회 + DESIGN 2회).
- **증상 3형태**: ① 이번 회차 변경과 무관한 **기존** 라우트가 404(다이나믹 세그먼트 아래 세그먼트가
  하나 더 있는 형태만 골라 깨짐) ② `ChunkLoadError`(500, 기존 청크가 깨짐) ③ **신규 모듈
  미인식**(새로 만든 파일을 포함하는 라우트가 200을 계속 반환하되 내용이 옛 버전 그대로,
  `touch`로 재저장해도 재컴파일 로그가 안 잡힘).
- **재현 조건**: 미확보. "여러 팀원이 같은 `.next`를 공유하며 각자 dev 서버를 기동·재기동하는
  상황"이 유력 후보로 적혀 있으나 5회 관찰 모두 인과를 확정하지 못했다.
- **해소법**: **프로세스 kill 후 단순 재시작으로는 그대로였고 `.next`(또는 `.next/dev`) 삭제
  후 재기동해야 풀렸다** — I-135와 정확히 반대되는 해소 서명.
- **핵심 특징**: 증상 ③(신규 모듈 미인식)이 I-135의 증상(재컴파일 시도 자체가 안 잡힘)과
  표면적으로 겹친다. 그런데 I-135는 재시작만으로 풀리고 I-139는 안 풀린다 — 같은 겉보기
  증상이 서로 다른 해소 서명을 가진 사례로, **증상만으로는 두 이슈를 구분할 수 없고 반드시
  "재시작 단독" 시험을 거쳐야 한다**는 팀의 기존 결론을 재확인한다.
- **36일차 팀장 실측 갱신 — 이번 실측 범위 밖.** 실험 C의 판별 절차가 첫 분기(재시작만
  시도)에서 바로 I-135로 해소돼, `.next` 삭제가 필요한 두 번째 분기(I-139 확정 재현)까지
  가지 않았다 — `/tmp/i139-dev-3.log`가 생성되지 않은 이유가 이것이다. I-139는 이번 회차에도
  **여전히 미재현·미확정으로 남는다.**

### 참고 선례 — I-083·I-087 (직접 배정 대상 아님, 판정 근거로만 인용)

`docs/ISSUES.md:3496`(I-083)와 `docs/ISSUES.md:3655`(I-087)은 "동시 다중 에이전트 파일 쓰기"라는
**같은 트리거**에서 출발했지만, I-083은 **런타임 모듈 그래프**(청크 매니페스트 읽기/쓰기 시점이
겹쳐 HTTP 응답 자체가 깨짐) 문제였고 I-087은 **빌드 타임 타입 검사 캐시**(`.next/dev/types`의
두 생성 파일이 서로 다른 시점 스냅샷으로 desync) 문제였다. CORE가 "트리거 계열은 같아도 자동으로

이번 판정에서 같은 논리를 그대로 적용한다.

**해석(원문, 실측 전)**: 두 열("에러 메시지 존재"·"산출물 자체 미생성")에서 I-048만 독보적으로
다르다 — 이건 "무엇을 쓰다가 실패했는지"가 명확한 유일한 이슈다. 반대로 "재시작만으로
충분한가" 행이 I-135를 나머지 둘과 가장 뚜렷하게 가른다. I-048과 I-139는 이 행에서 같은 값(❌)을
공유하지만, I-048은 "재현 조건이 두 개나 특정돼 있고 에러 메시지도 있다"는 점에서 I-139(재현
조건·증상 형태 모두 미확정)보다 훨씬 더 특정된 상태다 — 그래서 "I-048과 I-139가 완전히 동일한
결함"이라고 병합하는 것도 과도하다.

**해석 갱신(36일차, 실측 반영)**: 위 원문 해석은 "세 이슈 모두 실재하는 결함"이라는 전제
위에서 표의 각 행을 비교한 것이다. 실측 결과는 그 전제 자체를 건드린다 — I-048은 "재현 조건이
두 개나 특정돼 있다"는 것과 "그 두 조건을 실제로 재현해 봤더니 재현되지 않았다"는 것이
공존한다. 즉 표의 다른 행(에러 메시지·산출물 미생성 등)이 I-048을 다른 둘과 잘 구분해 주는
것은 여전히 사실이지만, **그 구분이 "다른 메커니즘의 실재하는 결함"을 가리키는 것인지 "과거에
관측됐으나 지금은 재현되지 않는 현상"을 가리키는 것인지는 이 표만으로 알 수 없다** — 실측을
거친 지금에야 I-135만 후자가 아니라 전자(확정 재현)임을 알 수 있다. **"클러스터 표에서 특징이
다르다"는 것과 "실측했더니 재현됐다"는 것은 다른 수준의 근거이고, 후자가 이번 회차의 실질적
결론이다.**

**CORE 교차검증 정정(36일차)**: CORE가 이 문서를 검증하며 "재시작 vs `.next` 삭제" 구분
기준의 원문(`docs/ISSUES.md:6342-6345`)은 **I-135 vs I-139**를 가르려고 쓰인 것이지 I-048을
같은 잣대로 잴 근거가 원문에 없다고 지적했다 — 맞는 지적이다. 위 표의 I-048 셀을 "DESIGN의
추론"으로 명시해 정정했다. 이 정정은 §0의 결론을 바꾸지 않는다 — 어차피 실험 A·B가 I-048
조건 ①·②를 재현하지 못했으므로, "재시작으로 충분한지"를 따지는 이 행 자체가 I-048에는 더
이상 실질적 의미가 없어졌다(재현된 현상이 없으니 그 현상의 해소 조건을 물을 수 없다).

## 3. 문서·설정·코드로 확인한 것

### 3.1 현재 `next.config.ts` (전문, `next.config.ts:1-17`)

```ts
const nextConfig: NextConfig = {
  reactCompiler: true,
  experimental: {
    globalNotFound: true,
  },
};
```

Turbopack 캐시·파일와처 관련 설정은 **전혀 없다** — I-048 원문이 "이번 회차엔 조사만 하고
설정은 바꾸지 않았다"고 적은 상태 그대로다(`docs/ISSUES.md:1031`). 즉 지금 이 저장소는 Next.js가
정하는 **기본값**을 그대로 쓰고 있다.

### 3.2 Turbopack 영속 캐시 — 존재 여부와 기본값 (인용: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/turbopackFileSystemCache.md`)

- 옵션은 실존한다: `experimental.turbopackFileSystemCacheForDev`(dev용)·
  `experimental.turbopackFileSystemCacheForBuild`(build용). "Turbopack이 `.next` 폴더에
  데이터를 저장·복원해 빌드 간 작업을 줄인다"(같은 문서 9행).
- **버전별 기본값 변경 이력**(같은 문서 42-48행 표):
  | 버전 | 변경 |
  | --- | --- |
  | v15.5.0 | canary에서 실험적으로 첫 릴리스 |
  | v16.0.0 | dev/build 분리된 플래그로 베타 릴리스 |
  | **v16.1.0** | **dev용 파일시스템 캐시가 기본으로 켜짐** |
- 이 저장소의 설치 버전은 **16.2.11**(`package.json` `"next": "16.2.11"`, `node_modules/next/package.json`
  `"version": "16.2.11"` 확인) — v16.1.0보다 위이므로 **`turbopackFileSystemCacheForDev`는
  지금 이 저장소에서 명시 설정 없이도 이미 켜져 있다.** build용은 여전히 opt-in(기본 꺼짐,
  `node_modules/next/dist/docs/01-app/03-api-reference/08-turbopack.md:259-260` 표: dev
  기본값 `true`, build 기본값 `false`).
- **판정에 대한 함의**: I-048의 SST/Compaction 에러 메시지는 이 파일시스템 캐시 저장 엔진의
  전형적 실패 문자열과 일치한다(RocksDB류 LSM-tree 저장소가 "SST 파일 쓰기 실패"·"압축 작업
  충돌"을 이런 문구로 던진다 — **다만 Turbopack의 내부 구현이 실제로 RocksDB인지는 Next.js
  공식 문서에 명시되어 있지 않다, 이 대응은 에러 메시지 패턴에 근거한 추정이며 미검증이다**).
  `next dev`는 기본으로 이 캐시가 켜져 있으니 **명시 설정을 아무것도 안 바꿔도 재현될 수 있다**는
  뜻이고, `next build`는 기본이 꺼져 있으니 I-048이 보고한 build 측 실패는 이 특정 실험적 캐시가
  아니라 **`.next` 디렉터리를 dev·build가 동시에 건드리는 더 일반적인 충돌**(§3.3)일 가능성이 더
  크다 — 이 구분은 재현 실험에서 갈라 봐야 한다(§4 실험 A).

### 3.3 "동시 dev+build" — Next 16이 이미 고쳤다고 주장하는 부분 (인용: `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md:918-922`)

> `next dev` and `next build` now use separate output directories, enabling concurrent
> execution. The `next dev` command outputs to `.next/dev`.
> Additionally, a lockfile mechanism prevents multiple `next dev` or `next build` instances
> on the same project.

- I-048의 재현 조건 ①(같은 저장소에서 `next dev`와 `next build`를 동시 실행)은 정확히 이
  변경사항이 다루는 시나리오다. Next 16은 dev/build 출력 디렉터리를 분리(`​.next/dev` vs `.next`)
  하고, **같은 종류 프로세스가 두 개 뜨는 것을 잠금 파일로 막는다**고 명시한다.
- **미확정으로 남기는 지점(중요)**: 이 잠금 메커니즘이 파일 잠금(`flock` 류)에 의존한다면,
  drvfs(WSL2의 Plan9/9P 기반 마운트, §3.4)에서 그 잠금 프리미티브 자체가 네이티브 Linux
  파일시스템과 동일하게 동작하는지는 **Next.js 문서도, 이 조사도 확인하지 못했다.** 즉 "Next 16이
  일반 환경에서는 이 문제를 고쳤다"는 것과 "drvfs에서도 그 방어가 실제로 작동한다"는 것은 별개
  주장이다 — 후자는 검증되지 않았고, **이것이 재현 실험 A의 핵심 질문이다**(§4).
- I-048 재현 조건 ①은 "동시 dev+build"였지 "동시 dev+dev"(여러 팀원이 각자 `npm run dev`)는
  아니었다는 점도 정확히 구분해야 한다 — 인용문의 "prevents multiple `next dev` … instances"는
  후자(여러 팀원이 각자 dev 서버)에 더 가깝고, 이건 I-139의 유력 후보 재현 조건("여러 팀원이 같은
  `.next`를 공유하며 각자 dev 서버를 기동")과 정확히 겹친다 — 만약 이 잠금이 실제로 작동한다면
  두 번째 `npm run dev`는 **조용히 캐시를 손상시키는 대신 명확한 에러로 거부**되어야 하는데,
  I-139는 그런 명확한 거부 로그를 보고한 적이 없다(증상 ①②③ 전부 "조용히 깨짐" 계열). 이 불일치
  자체가 실험할 가치가 있는 가설이다.

### 3.4 캐시 디렉터리를 WSL 네이티브 경로로 옮기는 안 — 존재하지 않는 옵션임을 확인 (인용: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/distDir.md:20`)

> `distDir` **should not** leave your project directory. For example, `../build` is an
> **invalid** directory.

- I-048 후속 제안 2번("캐시 디렉터리를 WSL 네이티브 파일시스템(`/home/...`)으로 옮기는 방안을
  검토한다")은 **`next.config.ts`의 `distDir` 옵션으로는 실행 불가능하다** — 이 저장소 자체가
  `/mnt/e/claudeStudy/...`(drvfs) 아래 있고, `distDir`은 프로젝트 루트를 벗어날 수 없다고 공식
  문서가 명시적으로 금지한다. `turbopack.root`(모듈 해석 루트, `node_modules/next/dist/docs/.../
  turbopack.md:97-124`)도 검토했지만 이건 **모듈 리졸브 루트**이지 빌드 산출물 출력 위치가
  아니다 — 관련 없는 옵션이다.
- **이 제안을 next.config.ts 설정으로는 기각한다.** 대안이 될 수 있는 것은 OS 레벨 워크어라운드
  (예: WSL 네이티브 경로에 실제 디렉터리를 만들고 프로젝트의 `.next`를 그 경로로 심볼릭 링크)
  뿐인데, 이건 **Next.js 설정이 아니라 셸/파일시스템 조작**이고, 이번 조사에서 시험하지 않았다 —
  §5(완화책 후보)에 "미검증, 리스크 있음"으로만 남긴다.
- **36일차 실험 F로 밝혀진 중요한 한계**: `.next`(빌드 산출물·캐시)만 네이티브 경로로 옮기는
  심볼릭 링크는 **I-135를 전혀 해결하지 못한다.** 실험 F가 재현·해소한 것은 "소스 파일
  (`src/app/sample/page.tsx` 등) 자체가 어느 파일시스템 위에 있는가"이지 `.next`의 위치가
  아니다 — Turbopack의 파일 워처는 소스 트리를 감시하는 것이지 `.next`를 감시하는 게 아니기
  때문이다. 즉 "캐시 디렉터리만 이동"이라는 원래 완화책 후보 자체가 **I-135의 원인을 다루지
  못하는 방향**이었다는 것이 이번 실측으로 드러났다 — I-135를 실제로 해결하려면 **소스
  디렉터리를 포함한 저장소 전체**를 네이티브 파일시스템으로 옮겨야 한다(§5 개정판 참고).

### 3.5 WSL2 drvfs의 inotify 한계 — 일반 지식이며 이 조사에서 새로 확인한 것과 그렇지 않은 것

**공식 Next.js 문서(`node_modules/next/dist/docs/`)에는 WSL·drvfs·inotify에 대한 실질적 논의가
없다 — 정정(36일차, CORE 교차검증)**: 원문은 "언급 0건"이라고 썼는데 이건 틀렸다. `grep -rli
wsl`을 다시 돌리면 3개 파일이 걸린다 — 그중 `01-app/01-getting-started/01-installation.md:51`
("Operating systems: macOS, Windows (including WSL), and Linux.")이 진짜 WSL 언급(지원
운영체제 목록에 이름만 나열, 실질적 논의는 없음)이고, 나머지 2건
(`02-guides/preserving-ui-state.md:522`의 "newsletter form", `03-api-reference/04-functions/
cacheLife.md:66`의 "newsletters")은 대소문자 무시 매칭이 "**n-e-w-s-l**-etter"의 "wsl"
부분문자열에 우연히 걸린 오탐이다. **정정된 결론**: 실질적 논의는 0건(OS 지원 목록에 스치는
언급 1건 제외)이며, drvfs·inotify 관련 논의는 여전히 0건이다 — 결론 자체(공식 문서가 이
문제를 다루지 않는다)는 바뀌지 않는다. 아래는 이번 회차에 웹 검색으로 확인한 외부 근거이며,
**이 프로젝트 코드나
Next.js 공식 문서로 검증된 것이 아니다:**

- Microsoft WSL 공식 리포의 기술 문서(`microsoft/WSL` repo, `doc/docs/technical-documentation/
  drvfs.md`)는 WSL2에서 `/mnt` 드라이브가 **Plan9 프로토콜 기반 파일 서버**(Windows 쪽에서
  `wslservice.exe`가 띄움, WSL2 VM이 여기 접속)로 마운트된다고 설명한다 — 이건 네이티브 Linux
  파일시스템이 아니라 **프로토콜을 통한 원격 마운트**라는 뜻이다. 이 문서 자체는 inotify·파일
  워칭을 전혀 언급하지 않는다(직접 확인, 언급 0건).
- `microsoft/WSL#4739`(공식 이슈, 미해결 상태)는 "**Windows 애플리케이션**이 만든 파일 변경은
  Linux 프로세스에게 inotify 알림으로 전달되지 않는다"고 명시한다. 다만 이 이슈는 명시적으로
  "Windows 앱이 만든 변경"을 문제 삼고 있고, **"WSL 프로세스 자신이 drvfs 파일을 수정한 경우"도
  같은 정도로 이벤트가 누락되는지는 이 이슈만으로 확정할 수 없다** — 제보자는 "WSL1에서는 이게
  잘 됐다"고만 적었을 뿐, WSL2에서 WSL측 프로세스가 만든 변경까지 문제인지는 별도 확인이
  필요하다.
- **이 프로젝트와의 접점**: 이 회차까지 관찰된 I-135 사례들은 전부 **에이전트(Claude Code, WSL
  프로세스)가 `Edit`/`sed` 등으로 파일을 고친 경우**였다 — Windows 네이티브 앱(VS Code
  Windows 쪽 등)이 만든 변경이 아니다. 즉 위에서 찾은 가장 근접한 공식 근거(#4739)가 정확히
  이 프로젝트의 재현 조건과 일치하는지는 **미확정이다.** "WSL2 drvfs가 inotify에 약하다"는
  결론 방향 자체는 이 조사에서도 뒤집히지 않았지만, **정확한 메커니즘(9P 프로토콜이 이벤트를
  아예 전달 안 하는지, 지연·유실만 있는지, WSL측 쓰기에도 적용되는지)은 미검증으로 남긴다.**
- **36일차 실험 D·F로 이 문단의 미확정 지점 하나가 풀렸다.** #4739는 "Windows 앱이 만든
  변경"만 명시했는데, 이 프로젝트의 실제 편집은 전부 WSL 프로세스가 만든 변경이라 그 이슈가
  정확히 들어맞는지 의문이었다. **실험 D는 WSL 프로세스가 만든 두 종류의 편집(제자리 쓰기·
  `sed -i`의 inode 교체)이 둘 다 100% 누락됨을 확인했고, 실험 F는 같은 WSL 프로세스·같은 편집
  방식을 네이티브 경로(`/home`)로 옮기면 즉시 반영됨을 대조군으로 확인했다.** 즉 **"WSL
  프로세스 자신이 만든 변경도 drvfs(v9fs)에서는 감지되지 않는다"는 것이 이 프로젝트 조건에서
  직접 실측으로 확인됐다** — #4739가 다루는 "Windows 앱 한정" 시나리오보다 이 프로젝트의 실제
  결함 범위가 더 넓다는 뜻이다. 다만 **9P 프로토콜 내부에서 정확히 무엇이 이벤트를 막는지**
  (커널 v9fs 클라이언트의 구현 한계인지, WSL2의 Plan9 서버 쪽 문제인지)는 여전히 미검증이다 —
  이건 Next.js·이 저장소의 범위를 벗어나 WSL 자체의 내부 구현 문제이므로 이 조사로는 더
  파고들 수 없다.

### 3.6 `watchOptions.pollIntervalMs` — 위치·존재 확인, 효과는 §5에서 무효로 판정 (인용: `node_modules/next/dist/server/config-shared.d.ts:1246`, `node_modules/next/dist/server/config-schema.js:721-723`)

- **존재 여부**: 실존한다. 다만 **`experimental` 아래가 아니라 최상위 `NextConfig` 키다** —
  `config-shared.d.ts:1244-1246`이 `watchOptions?: { pollIntervalMs?: number }`로,
  `config-schema.js:721-723`이 zod 스키마 `watchOptions: z.strictObject({ pollIntervalMs:
  z.number().positive().finite().optional() })`로 각각 최상위에 정의한다 — `experimental.
  watchOptions`가 아니다(팀장 실험 E가 처음 발견, 36일차).
- **효과**: §5.1(개정판 완화책 표)에서 다루듯, 36일차 팀장 실측(`pollIntervalMs: 1000`)으로
  **I-135를 해소하지 못했고, 오히려 `watch error` 11건의 부작용을 새로 만들었다.** 이 옵션
  자체는 실존하지만 이 결함에 대해서는 무효한 완화책이다 — 자세한 실측 로그와 부작용 분석은
  §5.1.

## 4. 재현 실험 프로토콜 — 팀장 실행용 (36일차: 팀장이 A·B·C를 실행하고 D·E·F로 확장했다)

**원칙**: 아래 각 실험은 독립적으로 실행 가능하고, 관측 지점(정확한 로그 문자열·파일 존재 여부)과
판정 기준을 미리 고정해 실행 후 판정이 갈리지 않게 했다. `npm run dev`/`npm run build`는 팀장만
실행한다는 규칙을 그대로 따른다 — 아래는 팀장이 그대로 복사해 실행할 명령이다.

**36일차 CORE 교차검증 정정(조건부 PASS)**: 원래 스크립트의 `until grep -q "Ready"; do sleep
1; done` 루프에 타임아웃이 없어, 하필 이 실험들이 시험하는 "Ready가 안 뜨는" 실패 시나리오
자체에서 스크립트가 무한 대기에 빠질 수 있다는 지적을 받았다 — 타당하다. 아래 스크립트는
전부 `for i in $(seq 1 60); do ... && break; sleep 1; done` 형태의 60초 상한 루프로 고쳤다
(팀장이 실제 실행할 때도 이 형태로 바꿔 돌렸다 — 문서를 실행한 형태에 맞춰 다음 사람이 그대로
재현할 수 있게 했다).

**36일차 실행 결과 총평**: A·B·C 세 프로토콜 모두 **셀렉터 조정 경고까지 포함해 판정이 한 번도
갈리지 않았다** — 설계한 그대로 실행 가능함이 실증됐다. 결과: A·B 재현 안 됨, C 재현됨(→
I-135). 팀장이 그 결과를 바탕으로 D·E·F 세 실험을 추가로 설계·실행해 I-135의 원인을
확정했다(D: 편집 방식 무관, E: `pollIntervalMs` 무효+부작용, F: drvfs 자체가 원인인 대조군).
각 실험 아래에 실제 결과를 주석으로 달았다.

### 실험 A — I-048 재현 조건 ①(동시 dev+build)이 Next 16.2.11에서 아직도 깨지는지

**[실행 완료, 36일차 팀장] 결과: 재현 안 됨.** `/tmp/i048-dev.log` — `✓ Ready in 3.4s`,
build exit 0, `Persisting failed|Compaction failed|SST file` 매치 0건, `.next/dev`가 `.next`와
별도 디렉터리로 실제 존재, build 이후 `GET /sample 200 in 17.6s`·`GET / 200 in 1596ms`.

**가장 먼저 실행할 것을 권한다** — §3.3의 미확정 지점을 직접 풀어 준다.

```bash
# 0. 클린 상태 확보
rm -rf .next
git status --porcelain   # 워킹트리 dirty 여부 기록해 둘 것

# 1. dev 서버를 백그라운드로 띄우고 Ready 로그까지 대기(최대 60초 — 무한 대기 방지,
#    36일차 CORE 지적: "Ready가 안 뜨는" 시나리오 자체를 시험하는 실험이라 무한 루프면
#    그 실패 모드에서 스크립트가 멈춘다. 팀장이 실제 실행 시 이 형태로 고쳐 돌렸다)
npm run dev > /tmp/i048-dev.log 2>&1 &
DEV_PID=$!
for i in $(seq 1 60); do grep -q "Ready" /tmp/i048-dev.log && break; sleep 1; done
grep -q "Ready" /tmp/i048-dev.log || echo "경고: 60초 내 Ready 미도달 — 그 자체가 실험 A의 재현 신호일 수 있다"
cat /tmp/i048-dev.log

# 2. dev가 떠 있는 채로 build 실행
npm run build > /tmp/i048-build.log 2>&1
echo "build exit code: $?"

# 3. 관측
grep -E "Persisting failed|Compaction failed|SST file" /tmp/i048-dev.log /tmp/i048-build.log
ls -la .next/routes-manifest.json .next/dev 2>&1
curl -s -o /dev/null -w "dev server /sample: %{http_code}\n" http://localhost:3000/sample

# 4. 정리
kill $DEV_PID 2>/dev/null
```

- **기대 결과(문서상 "고쳐졌음"이 맞다면)**: 2번 build가 exit code 0으로 끝나고, 3번의 grep이
  0건, `.next/routes-manifest.json`이 존재, dev 서버는 build 이후에도 `/sample`에 200을 반환.
- **재현됨(=I-048이 이 버전에서도 살아있음) 판정 기준**: 위 grep이 1건 이상 매치되거나,
  `routes-manifest.json`이 없거나, build 이후 curl이 500을 반환하면 **재현됨**.
- **재현 안 됨 판정 기준**: 위 세 관측 전부 "기대 결과"와 일치하면 **재현 안 됨** — 이 경우
  I-048의 조건 ①은 Next 16 업그레이드로 이미 해소된 것으로 잠정 결론하고 이슈 본문에 그 사실만
  추가하면 된다(재현 안 됨 자체가 "결함 없음"을 증명하지는 않으므로 상태를 "해결됨"으로 바꾸지는
  말 것 — 조건 ②·③은 별도 실험이 필요하다).

### 실험 B — I-048 재현 조건 ②(abrupt kill → 재시작)

**[실행 완료, 36일차 팀장] 결과: 재현 안 됨.** 워밍업으로 `/sample`·`/login`을 컴파일시켜
캐시를 실제로 쓰게 한 뒤(`/tmp/i048b-1.log`) `kill -9` → 재기동(`/tmp/i048b-2.log`: `✓ Ready
in 4.2s`), SST/Compaction 0건, `GET /sample 200 in 8.9s`.

```bash
rm -rf .next
npm run dev > /tmp/i048b-1.log 2>&1 &
DEV_PID=$!
for i in $(seq 1 60); do grep -q "Ready" /tmp/i048b-1.log && break; sleep 1; done  # 60초 상한(무한 대기 방지)

kill -9 $DEV_PID   # graceful shutdown 생략 — 조건 ②의 핵심
sleep 1

npm run dev > /tmp/i048b-2.log 2>&1 &
DEV_PID2=$!
sleep 15   # Ready 로그가 안 뜨는 경우까지 대비해 고정 대기
grep -E "Persisting failed|Compaction failed|SST file" /tmp/i048b-2.log
grep -q "Ready" /tmp/i048b-2.log && echo "Ready 도달" || echo "Ready 미도달(15초 내)"
curl -s -o /dev/null -w "재시작 후 /sample: %{http_code}\n" http://localhost:3000/sample
kill $DEV_PID2 2>/dev/null
```

- **재현됨 판정 기준**: SST/Compaction 문자열 매치, 또는 15초 내 "Ready" 미도달, 또는 curl이
  500/000(연결 거부).
- **재현 안 됨 판정 기준**: 세 조건 모두 정상.

### 실험 C — I-135 vs I-139 판별 (팀이 이미 정한 구분 절차를 그대로 스크립트화)

**[실행 완료, 36일차 팀장] 결과: 재현됨 → I-135로 확정.** 5초 대기에도 `<h1>` 불변, dev 로그에
재컴파일 시도 없음(`/tmp/i135-dev.log`). `.next` 안 지우고 재시작만 → 반영됨(`/tmp/
i135-dev-2.log`) → **I-135 계열로 확정**(`.next` 삭제 분기 `/tmp/i139-dev-3.log`는 생성되지
않음 — 첫 분기에서 이미 해소돼 도달할 필요가 없었다). 셀렉터(`<h1>` 매칭)는 실제 마크업과
그대로 맞아 조정이 필요 없었다.

```bash
rm -rf .next
npm run dev > /tmp/i135-dev.log 2>&1 &
DEV_PID=$!
for i in $(seq 1 60); do grep -q "Ready" /tmp/i135-dev.log && break; sleep 1; done  # 60초 상한

# 1. 이미 렌더되는 라우트의 텍스트를 바꿔 저장 (예: src/app/sample/page.tsx의 <h1> 문구)
#    실제 텍스트 변경은 팀장이 직접 한 줄 편집 후 저장
BEFORE=$(curl -s http://localhost:3000/sample | grep -o "<h1[^<]*</h1>" | head -1)
echo "변경 전: $BEFORE"
# --- 여기서 파일을 편집하고 저장 ---
sleep 3
AFTER=$(curl -s http://localhost:3000/sample | grep -o "<h1[^<]*</h1>" | head -1)
echo "변경 후(재컴파일 대기 3초): $AFTER"

if [ "$BEFORE" = "$AFTER" ]; then
  echo "반영 안 됨 — 구분 절차 진입"
  PID_BEFORE_RESTART=$(pgrep -f "next dev" | head -1)
  kill $PID_BEFORE_RESTART   # .next는 지우지 않는다 — 이게 구분 절차의 핵심
  sleep 1
  npm run dev > /tmp/i135-dev-2.log 2>&1 &
  for i in $(seq 1 60); do grep -q "Ready" /tmp/i135-dev-2.log && break; sleep 1; done  # 60초 상한
  sleep 3
  AFTER_RESTART=$(curl -s http://localhost:3000/sample | grep -o "<h1[^<]*</h1>" | head -1)
  echo "재시작 후(.next 안 지움): $AFTER_RESTART"
  if [ "$AFTER_RESTART" = "$AFTER" ]; then
    echo "판정: I-139 계열(재시작만으로 안 풀림) — 이제 .next 삭제로 재시험"
    kill $(pgrep -f "next dev") 2>/dev/null
    rm -rf .next
    npm run dev > /tmp/i139-dev-3.log 2>&1 &
    for i in $(seq 1 60); do grep -q "Ready" /tmp/i139-dev-3.log && break; sleep 1; done  # 60초 상한
    sleep 3
    curl -s http://localhost:3000/sample | grep -o "<h1[^<]*</h1>" | head -1
    echo "위 결과가 실제 변경 내용과 일치하면 .next 삭제로 해소 = I-139 확정 재현"
  else
    echo "판정: I-135 계열(재시작만으로 해소됨)"
  fi
else
  echo "판정: 이번엔 재현 안 됨(정상 반영) — HMR 정상 동작"
fi
kill $(pgrep -f "next dev") 2>/dev/null
```

- **관측 지점**: `curl`로 받은 `<h1>` 텍스트 문자열 자체를 비교(눈으로 브라우저를 볼 필요 없이
  판정 가능하게 했다). 추가로 `/tmp/i135-dev*.log`에 해당 파일 경로의 "Compiled"/"compiling"
  로그가 찍히는지도 같이 확인하면 "재컴파일 시도 자체가 없었는지"를 이중으로 검증할 수 있다:
  `grep "sample/page" /tmp/i135-dev.log`
- **판정 기준**: 위 스크립트가 스스로 "I-135 계열"/"I-139 계열"/"재현 안 됨"을 출력한다 —
  사람이 로그를 해석할 필요가 없도록 만들었다. 다만 스크립트의 `curl`/`grep` 문자열 매칭이
  실제 `<h1>` 태그 구조와 다를 수 있으니(shadcn 컴포넌트가 `<h1>`을 직접 안 쓸 수도 있음)
  **팀장이 실행 전에 대상 라우트의 실제 마크업을 한 번 확인하고 셀렉터를 조정할 것.**

### 실험 D — (36일차 팀장 확장, 실행 완료) 편집 방식이 변수인가

**가설**: "`sed -i`가 임시 파일을 만들고 rename해서 inode를 교체하기 때문에 워처가 놓친다" —
즉 편집 도구를 제자리 쓰기(in-place write)로 바꾸면 I-135가 사라질 수 있다는 가설.

**방법**: 두 편집 방식을 대조했다 — ① 제자리 쓰기(Python `open(path, 'w')` + `f.flush()` +
`os.fsync()`, inode 유지 확인: `stat -c %i` 결과 `27584547718228090`로 편집 전후 동일) ②
`sed -i`(inode 교체 확인: `27866022694938746` → `27303072741517492`).

**결과**: **둘 다 누락.** `/tmp/expD-dev.log`는 최초 1회 `○ Compiling /sample ...` 이후 8회
연속 `GET /sample` 요청에서도 재컴파일 로그가 전혀 없다.

**판정**: 가설 기각. 편집 방식(inode 교체 여부)은 변수가 아니다 — 이 구성에서는 편집 방식과
무관하게 항상 누락된다.

### 실험 E — (36일차 팀장 확장, 실행 완료) `watchOptions.pollIntervalMs` 완화책 실측

**가설**: Turbopack이 이벤트 기반 워처 대신 폴링으로 전환하면(다른 도구들의 일반적인 drvfs
우회책과 같은 방향) I-135가 해소될 수 있다.

**방법**: `next.config.ts` 최상위에 `watchOptions: { pollIntervalMs: 1000 }`을 추가(§3.6 —
`experimental` 아래가 아니라 최상위 키임을 먼저 확인한 뒤 적용)하고 실험 C와 같은 절차로
재시험.

**결과**: **효과 없음 + 부작용.** 편집은 여전히 반영되지 않았고, 대신 `/tmp/expE-dev.log`에
`watch error` **11건**이 새로 발생했다 — 전부 `Io(Os { code: 2, kind: NotFound })`(존재하지
않는 경로를 폴링하려 함). 예: `watch error (["…/node_modules/next/dist/compiled/@next/
react-refresh-utils/internal"]): Io(Os { code: 2, kind: NotFound, message: "No such file or
directory" })` — 그 디렉터리 밑에는 실제로 `dist`만 있다. 이 에러는 **폴링을 켠 이번 실행에만
나타났다**(비폴링 실행 6개 로그에는 0건) — I-135의 원인이 아니라 폴링 활성화의 부작용이다.
`next.config.ts`는 실험 후 원복했다(`git status --porcelain -- next.config.ts` 클린 확인,
DESIGN이 이 문서 갱신 시점에 재확인).

**판정**: `pollIntervalMs`는 실존하는 옵션이지만 이 결함에는 **실측으로 무효** — §5에서
완화책 후보에서 제외한다.

### 실험 F — (36일차 팀장 확장, 실행 완료) drvfs 대조군 — I-135의 원인을 확정한 실험

**문제의식**: 팀은 4회 관찰 내내 "drvfs 때문일 것"이라고 **가정만** 하고 한 번도 대조군을 두지
않았다.

**방법**: 저장소를 `node_modules`째 WSL 네이티브 경로(`/home`)로 복사해, 같은 Next.js
버전(16.2.11)·같은 편집 방식(`sed -i`)·같은 대기 시간(8초)으로 두 위치를 대조했다.

**결과**:
- `/mnt/e`(`stat -f` 리포트 타입: `v9fs`): 누락, 재컴파일 로그 없음(기존 관찰과 동일).
- `/home`(`ext2`/`ext3`): **`✓ Compiled in 36ms`로 즉시 반영, `watch error` 0건**
  (`/tmp/expF-dev.log`).

**판정**: 파일시스템 외 모든 변수(Next 버전·편집 방식·대기 시간)를 고정한 상태에서 마운트
위치만 바꿔 결과가 갈렸으므로, **I-135의 원인은 Turbopack 자체도, 편집 방식도, 영속 캐시도
아니라 마운트 파일시스템(v9fs/drvfs)이다.** 대조군 디렉터리는 실험 후 삭제됐다.

**주의(§3.4 갱신 참고)**: 이 실험이 옮긴 것은 저장소 **전체**(소스 + `node_modules`)다 —
`.next`만 네이티브 경로로 옮기는 것과는 다르다. §5.1이 이 구분을 완화책 표에 반영한다.

## 5. 완화책 — 비용·리스크 (36일차 실측 반영, 최종판)

### 5.0 무엇이 바뀌었나

원안(§0.1 참고)은 "완화책 A(캐시 끄기)가 유력, B'(심볼릭 링크)은 미검증"으로 정리했다.
실측 결과 **완화책 A는 조준점이 틀렸다** — 확정 재현된 결함(I-135)은 캐시 축이 아니라 워처
축이고, 팀장이 추가로 실측한 폴링 기반 후보(`pollIntervalMs`)도 무효로 확인됐다. **실측으로
유일하게 효과가 확인된 것은 "네이티브 파일시스템으로 옮기기"**이며, 그 효과는 `.next`만
옮겨서는 안 되고 **소스 트리를 포함한 저장소 전체**를 옮겨야 나온다(실험 F).

**팀장 지시(36일차 마무리 조건) 반영**: 실측으로 무효 판정된 안(`pollIntervalMs`)과 조준점이
어긋난 안(`turbopackFileSystemCacheForDev`)을 "채택 가능한 완화책" 목록에 그대로 남기지
않는다. 아래 §5.1을 **지금 실제로 남는 완화책 두 가지만** 담게 다시 쓰고, 시험·기각한 나머지는
§5.2에 "기록용"으로만 분리했다.

### 5.1 지금 남는 완화책 — 딱 둘뿐이다

| 완화책 | 무엇인가 | 비용 | 리스크 | 권장 |
| --- | --- | --- | --- | --- |
| **① "재시작 우선" 운영 규칙 명문화** | 코드를 고쳤는데 dev 서버 반영이 안 되면, `.next`를 지우기 전에 먼저 프로세스 재시작만 시도한다 | 낮음 — 문서화 비용만 | 낮음 | ✅ **즉시 적용 권장.** 실험 C가 이 규칙 그대로 실행해 정확히 작동함을 재확인했다(재시작 단독으로 I-135 100% 해소) |
| **② 저장소 전체를 WSL 네이티브 파일시스템으로 재배치** | 소스+`node_modules`를 포함한 저장소 전체를 `/mnt/e`(v9fs)에서 `/home`류 네이티브 경로(`ext2`/`ext3`/`ext4`)로 옮긴다 | **높음** — 이 문서를 포함한 프로젝트 문서 다수가 `/mnt/e/claudeStudy/workspaces/tProject/mo_im` 절대경로를 참조한다(재검색·치환 필요), Windows 쪽 직접 열람은 `\\wsl$\`/`\\wsl.localhost\` UNC 경로로 접근 방식이 바뀐다, 여러 세션이 공유하는 경로 규약 재점검 필요 | **비용이 큰 유일한 실효책이다 — 정직하게 그렇게만 말한다.** 실측(실험 F, `/home`에서 `✓ Compiled in 36ms`)으로 효과는 확인됐지만, 이 팀이 지금 당장 채택할 수 있는 성격의 변경이 아니다(코드 한 줄이 아니라 저장소 운영 방식 자체를 바꾸는 결정) | **제안만 한다, 적용 여부는 결정하지 않는다.** "얼마나 자주 I-135에 부딪히는지" 대 "재배치 비용"을 사용자·팀장이 판단할 사안 |

이 두 가지 외에는 **완화책으로 남겨 두는 것이 없다** — ①은 지금 결함 앞에서 실제로 통하는
유일한 무비용 대응이고, ②는 비용이 크지만 실측으로 검증된 유일한 근본 해결책이다. 나머지는
전부 시험 후 기각됐다(§5.2).

### 5.2 시험·기각한 것 (기록용 — 완화책 후보가 아니다)

**아래는 "다음에 또 제안되지 않도록" 남기는 실패 기록이다. 재검토 후보 목록이 아니다.**

| 시험한 것 | Next 16에 실존하는가 | 왜 기각됐는가 |
| --- | --- | --- |
| `experimental.turbopackFileSystemCacheForDev: false` | ✅ 존재(§3.2) | **조준점이 틀렸다.** 이 옵션은 온디스크 컴파일 캐시 축(I-048·I-139가 있다면 그쪽)을 다루는데, 이번에 확정 재현된 결함(I-135)은 파일 워처 축이라 애초에 무관하다. I-048·I-139 자체가 이번엔 재현 안 됨/미실험이라 이 옵션의 실제 효과를 잴 대상조차 없었다 — **완화책이 아니라 "겨냥이 어긋난 옵션"으로 기록만 한다.** I-048·I-139가 실제로 재현되는 다음 기회가 오면 그때 처음부터 다시 검토해야 한다(지금 목록에 "보류 후보"로도 남기지 않는다 — 재현되지 않은 결함을 위한 완화책을 지금 준비해 둘 근거가 없다) |
| `watchOptions.pollIntervalMs`(폴링) | ✅ 존재(§3.6, 최상위 키) | **실측 무효 + 부작용.** `pollIntervalMs: 1000`으로도 I-135는 그대로 재현됐고, 오히려 `watch error` 11건이 새로 발생했다(§4 실험 E, `docs/ISSUES.draft.DESIGN.md`에 별도 기록) |
| `distDir`로 캐시를 WSL 네이티브 경로로 이동 | ❌ 존재하지 않음(§3.4) | `distDir`이 프로젝트 디렉터리를 벗어날 수 없다고 공식 문서가 명시 — 애초에 존재하지 않는 옵션이라 시험 대상도 아니었다 |
| `.next`만 심볼릭 링크로 네이티브 경로에 우회 | Next.js 설정 아님, OS 레벨 조작 | 실험 F로 **I-135에는 효과가 없다는 것이 사실상 확정**됐다 — I-135는 소스 파일 감시 문제라 `.next`의 물리적 위치와 무관하다(§3.4 갱신). I-048·I-139(온디스크 캐시 축)에는 도움될 가능성이 이론상 남지만, 그 축 자체가 이번엔 재현되지 않아 검증 기회가 없었다 |
| `next build --webpack`/`next dev --webpack`으로 전환 | ✅ 존재 | 번들러 전체 교체는 "완화책"이 아니라 아키텍처 결정이다 — 이번 배정 범위를 넘는다고 판단해 시험하지 않았고 권장하지도 않는다 |

## 6. 이 조사가 미검증으로 남긴 것 (36일차 갱신)

1. ~~세 이슈 모두 정확한 유발 조건은 여전히 미확보다~~ → **부분 해소.** I-135는 실측으로
   원인(drvfs/v9fs)까지 확정됐다(실험 D·F). I-048은 조건 ①·②가 재현되지 않는다는 것까지는
   확인됐지만 "그럼 원래 왜 재현됐었는지"는 여전히 미확정이다(과거 관찰 3회가 다른 버전·다른
   조건이었을 가능성, 또는 조건 ③처럼 결정론적으로 재현 불가능한 경로였을 가능성 — 어느
   쪽인지 이번 실측으로는 가릴 수 없다). I-139는 이번에도 전혀 실험되지 않았다.
2. **Turbopack의 영속 캐시가 실제로 RocksDB(또는 유사 LSM-tree 저장소)로 구현됐는지**는

## 7. 용어 노트 — "drvfs"와 "v9fs"

- 이 문서와 `docs/ISSUES.md`의 I-048·I-135·I-139는 전부 **"drvfs"**를 써 왔다 — Microsoft의
  공식 WSL 기술 문서(`microsoft/WSL` repo, `doc/docs/technical-documentation/drvfs.md`, §3.5
  인용)도 `/mnt` 마운트포인트를 이 이름으로 부른다. 다만 그 문서 자신이 "WSL1은 drvfs로 직접
  마운트하고, WSL2 이후는 plan9·virtio-plan9·virtiofs로 마운트한다"고 구분해 적는다 — **"drvfs"는
  마운트포인트 관례상의 이름이지, WSL2가 실제로 쓰는 커널 파일시스템 드라이버 이름이
  아니다.**
- 36일차 실험 F에서 `stat -f`로 이 저장소 경로(`/mnt/e/claudeStudy/...`)의 실제 파일시스템
  타입을 직접 확인한 결과는 **`v9fs`**였다 — Linux 커널이 9P 프로토콜 클라이언트에 쓰는 실제
  드라이버 이름이다(WSL2가 Windows 쪽 Plan9 서버에 9P로 접속하는 구성과 일치, §3.5의
  `wslservice.exe`/Plan9 서버 설명과도 부합).
- **이 문서의 표기 결정**: 이 문서를 포함해 새로 쓰는 글에서는 **"WSL2 drvfs(`stat -f` 실제
  타입은 `v9fs`) 마운트"**처럼 두 이름을 함께 적는다 — "drvfs"는 이 프로젝트의 기존 이슈
  제목·본문(`docs/ISSUES.md`)에 이미 광범위하게 박혀 있는 사용자 대면 이름이라 갑자기 없애면
  검색·인용이 끊기고, "v9fs"는 이번에 처음 실측으로 확인한 정확한 기술 용어라 근거를 남길
  가치가 있다. **기존 `docs/ISSUES.md`의 I-048·I-135·I-139 제목·본문은 이번 회차에 고치지
  않았다** — 그 문서들을 다시 여는 사람(팀장 또는 원 제보자)이 필요하면 이 절을 인용해 후속
  으로 정정할 수 있게 남겨 둔다(D-082 기준 "이미 번호가 있는 블록 내부 상태 갱신"에 해당하므로
  팀장·원 제보자가 직접 고쳐도 되고, DESIGN이 대신 고치지도 않았다 — 이 실측이 DESIGN 소관
  실험이 아니라 팀장이 실행한 실험이라 귀속을 명확히 하기 위함이다).
