# "표시 층 실렌더 감사" 절차화 — 33일차, DESIGN

32일차 트리아지 §6·워크로그의 결론("새 SQL 축을 파는 것보다 기존 결정·판정의 표시 층을
실렌더로 확인하는 쪽이 수확이 컸다" — I-151이 그 축에서 나온 (A) 1건)을 이번 회차에
재현 가능한 절차로 만든다. 이 문서는 **방법 자체**를 남기는 것이 목적이고, 이번 회차
실행 결과는 부산물이다 — 다음 사람이 이 절차를 그대로 다시 돌릴 수 있어야 한다.

**정직 고지(갱신, 33일차 종료 시점)**: 이번 회차는 **실제 브라우저 렌더 확인을 최종
1건 완료했다** — 1순위 D-048, §7 참고(팀장이 브라우저 락 교착 끝에 직접 실행). 회차
대부분은 브라우저 없이 모집단 추출·정렬·최우선 후보의 **코드 레벨 재추적**으로 채워졌고
(브라우저는 BOARD의 I-082 강제 재현이 이번 회차 1순위였다), 회차 막바지에 브라우저가
열려 D-048 실렌더가 실제로 실행됐다 — **이 문서가 32일차부터 이어진 "표시 층 실렌더가
새 SQL 축보다 수확이 크다"는 축을 이번 회차에도 실제로 성립시킨 사례**다. 아래 1~3절은
**방법·모집단·후보**이고, 4절이 **실제로 한 일과 안 한 일**을 가른다.

## 0. 왜 이 문서가 필요한가

I-158(배정 1, 같은 회차)이 정확히 같은 함정을 다시 보여줬다 — `getCrewById`의 docstring이
"이 폴백이 새 소비자에서 위험할 수 있다"를 명시적으로 예고했는데도, 그 예고와 실제 코드
변경을 **대조하는 절차가 없어서** 11일 동안(21→32일차) 아무도 확인하지 않았다. "코드가
경고했다"와 "실제로 확인했다"는 다른 것이고, 이 프로젝트에는 그 둘을 잇는 표준 절차가
없었다. 이 문서가 그 절차를 만든다.

**같은 회차 다른 축에서 나온 사례(BOARD, I-082)도 같은 계통이다.** BOARD가 I-082를
재현·수정하는 과정에서 **21일차 이슈 원문의 서술 하나를 실측으로 뒤집었다** — "재탐색
(SPA 내비게이션)만으로 자연 회복된다"는 원문 서술이 **틀렸다**(SPA 내비게이션으로는
토큰 재요청 자체가 없고, 하드 리로드만 실제로 복구시킨다). 31일차가 추정했던 콘솔 로그
줄 수도 1줄이 아니라 **2줄**(벨+토스트)로 정정됐다. **12회차 동안(21→33일차) 이슈
문서에 남아 있던 서술이 코드 읽기·부분 관찰에 기반했고, 실측이 그걸 뒤집었다** — I-158과
정확히 같은 실패 모양(문서에 적힌 판단이 실측 없이 오래 방치된다)이 이번 회차에만
두 번 독립적으로 나왔다는 뜻이라, 이 감사가 다루는 문제가 우연이 아님을 보여주는 근거로
남긴다.

## 1. 모집단 정의와 추출 방법

**기준**: "데이터·값·SQL은 맞다"까지만 검증되고 "화면에 어떻게 나오는가"는 검증되지 않은
판정. 구체적으로: 판정 근거 텍스트에 SQL/REST 실측 마커가 있고, 브라우저/실렌더 마커가
**없는** `docs/ISSUES.md`의 `### I-\d+` 블록과 `docs/prioritization-and-risks.md`의
`### D-\d+` 블록.

**마커 정의**:

- SQL 실측 마커(있으면 1차 후보): `SQL 실측`·`begin…rollback`(및 표기 변형)·`서비스롤`·
  `service_role`·`execute_sql`·`REST 실증`·`REST로 확인`·`psql`
- 브라우저 실측 마커(있으면 후보에서 제외): `브라우저`·`실렌더`·`DOM`·`스냅샷`·`snapshot`·
  `playwright`·`browser_*`

### 1.1 33일차 CREW 교차검증 — ⓔ FAIL, 최초 버전은 재현되지 않았다

최초 버전은 위 마커를 **원문에 그대로**(마크다운 강조·백틱 제거 없이) 정규식 매칭해
"I-* 15건, D-* 6건 = 21건"을 얻었다고 적었다. **CREW가 같은 기준을 파이썬으로 독립
재구현해 재현을 시도했고, 실패했다** — `` `begin`…`rollback` `` 처럼 SQL 코드용 백틱이
"begin"과 "rollback" 사이에 끼는 경우(예: D-048)가 실제 문서에 흔한데, 원문 그대로 매칭한
정규식은 이 경우를 놓친다. **결과: D-048(이 문서가 1순위로 꼽은 바로 그 후보)이 원문
그대로 매칭에서는 잡히지 않는다** — 원 버전이 "이 grep으로 21건이 나온다"고 적어 놓고
정작 그 grep으로는 자신이 1순위로 꼽은 항목 자체를 못 찾는 모순이 있었다. **재현
불가능한 산출물을 재현 가능하다고 적은 것이 이 배정의 핵심 실패였다** — 아래 1.2가
고친 버전이다.

### 1.2 고친 방법 — 정규화 단계를 명시하고, 그 산출물을 그대로 적는다

**정규화는 두 단계다 — 성격이 다르므로 구분해서 적는다.**

1. **백틱(`` ` ``)·마크다운 굵게 표시(`**`) 제거. 밑줄(`_`)·홑 별표(`*`)는 건드리지
   않는다** — 이 문서 안에서 `service_role`·`crew_memberships`처럼 식별자 내부에 밑줄이
   들어간 마커가 많아서, 밑줄까지 지우면 `service_role`이 `servicerole`이 되어 그 마커
   자신이 매칭에서 빠지는 자기모순이 생긴다(33일차 재구현 중 실제로 이 실수를 한 번 했다
   — 처음 시도한 "구두점 전부 제거" 정규화는 I-* 17건·D-* 7건만 나왔는데, 원인을 추적해
   보니 밑줄 제거가 `service_role` 마커 자체를 깨뜨리고 있었다). **이건 정규화 폭을
   잘못 넓힌 실수였다** — 마커가 아닌 것까지 건드려서 마커 자신이 깨졌다.
2. **공백류(개행 포함)를 단일 스페이스로 정규화한다**(`re.sub(r'\s+', ' ', text)`,
   33일차 CREW 교차검증이 지적하고 팀장이 채택 — ⓔ 재검증 후속). **이건 성격이 다르다** —
   폭을 넓히는 게 아니라 **"의미가 같은 것을 같게 만드는" 정규화**다. `"SQL 실측"`이라는
   한 구절이 마크다운 문단 폭 때문에 우연히 `"...SQL\n  실측..."`처럼 줄바꿈으로 갈리는
   경우(I-108이 실제 사례 — 아래)가 있는데, 원문 그대로 매칭하면 **내용이 한 글자도 안
   바뀌어도 문단 앞쪽 단어 하나만 늘어나 줄바꿈 위치가 바뀌면 모집단 수가 달라진다.**
   1단계(구두점 제거)와 2단계(공백 정규화)를 같은 종류의 "정규화 넓히기 위험"으로
   묶으면 안 된다 — 1단계는 실제로 위험했고(마커 자체가 깨짐), 2단계는 "같은 구절의
   시각적 우연"만 없앤다(마커가 뜻하는 개념 자체는 바뀌지 않는다).

**재현성 기준의 성립 조건**: "정수 일치가 아니라 스크립트 재실행 가능성"을 재현성의
기준으로 삼는다고 §1의 다른 절에 적었는데, **그 기준이 성립하려면 스크립트 자신이 문서의
흔한 서식 변형(줄바꿈 재배치)에 안정적이어야 한다는 전제가 필요하다.** 그 전제가 깨져
있으면(2단계 정규화 이전 상태) "스크립트를 그대로 돌리면 같은 목록이 나온다"는 것만으로는
부족하다 — 문서 본문이 한 글자도 안 바뀌어도 줄바꿈만 재배치되면 같은 스크립트가 다른
결과를 낸다. 2단계 정규화가 이 전제를 다시 성립시킨다.

**스크립트(그대로 실행 가능, 이 문서의 유일한 정본)**:

```python
import re

def split_blocks(path, header_re):
    lines = open(path, encoding='utf-8').read().split('\n')
    blocks, cur_id, cur_title, cur_start = [], None, None, None
    for i, line in enumerate(lines):
        m = re.match(header_re, line)
        if m:
            if cur_id:
                blocks.append((cur_id, '\n'.join(lines[cur_start:i])))
            cur_id, cur_start = m.group(1), i
    if cur_id:
        blocks.append((cur_id, '\n'.join(lines[cur_start:])))
    return blocks

def normalize(text):
    text = text.replace('`', '').replace('**', '')  # 1단계: 백틱·굵게만 제거, _ 는 안 건드림
    text = re.sub(r'\s+', ' ', text)                 # 2단계: 공백류(개행 포함)를 한 칸으로
    return text

SQL_MARKERS = re.compile(
    r"SQL 실측|begin[…\.]{1,3}rollback|서비스롤|service_role|execute_sql|"
    r"REST 실증|REST로 확인|psql", re.I)
BROWSER_MARKERS = re.compile(
    r"브라우저|실렌더|(?<![a-zA-Z])DOM(?![a-zA-Z])|스냅샷|snapshot|playwright|browser_", re.I)

issues = split_blocks('docs/ISSUES.md', r'^### (I-\d+)')
decisions = split_blocks('docs/prioritization-and-risks.md', r'^### (D-\d+)')

cand_i = [id_ for id_, body in issues
          if SQL_MARKERS.search(normalize(body)) and not BROWSER_MARKERS.search(normalize(body))]
cand_d = [id_ for id_, body in decisions
          if SQL_MARKERS.search(normalize(body)) and not BROWSER_MARKERS.search(normalize(body))]
```

**패치 이력(33일차, CREW 재검증 → 팀장 채택)**: 이전 버전은 `실측\(SQL|rollback\)`이라는
우회 분기를 SQL 마커에 추가해 I-108 한 건만 임시로 잡았었다 — **근본 원인(줄바꿈이 구절을
가른다)을 안 고치고 증상 하나만 덮은 것**이라 같은 원인의 다른 구절(예: `begin` … `rollback`
이 줄바꿈으로 갈리는 경우)은 여전히 놓쳤다. 이번에 그 우회 분기를 제거하고 2단계
정규화로 교체했다 — 원인 자체를 없앴다.

**이 스크립트를 33일차 시점 문서에 실행한 결과(공백 정규화 패치 후 재확인, 이 숫자가 이
문서의 최종 모집단이다)**:

```
I-* (26건): I-030, I-038, I-057, I-062, I-075, I-079, I-086, I-089, I-090,
  I-091, I-092, I-094, I-100, I-108, I-111, I-120, I-121, I-124, I-137,
  I-141, I-146, I-147, I-148, I-149, I-155, I-156
D-* (9건): D-037, D-048, D-050, D-054, D-055, D-056, D-058, D-073, D-074
```

**총 35건**(26+9). 패치 전(§1.2 위 문단들이 다루는 백틱·굵게만 제거한 버전)은 **33건
(24+9)**이었다 — 공백 정규화 패치로 **정확히 2건이 늘었는데, 원인이 서로 다르다**:

- **I-108**(신규 포함) — **진짜 스크립트 버그였다.** SQL 근거 문구 `"...교차검증 SQL
  실측(직접 조회...)"`이 문단 폭 때문에 우연히 `"SQL"`과 `"실측"` 사이에서 줄바꿈됐다.
  패치 전 스크립트는 `"SQL 실측"`(공백 1개 고정)을 리터럴로 찾아 이 줄바꿈을 못 넘었다 —
  33일차 CREW 교차검증이 `SQL\s*실측`(개행 포함 매칭)으로 이 건을 잡아 특정했다.
  **문서 내용은 한 글자도 안 바뀌었는데 줄바꿈 위치만 우연이었어도 모집단이 달라지는
  사례**였다 — 이게 §1.2의 재현성 성립 조건("스크립트가 서식 변형에 안정적이어야 한다")이
  요구하는 바로 그 안정성이다.
- **I-108이 아니라 §1.2 이전 버전이 갖고 있던 `실측\(SQL|rollback\)` 우회 분기는 이 건
  하나만 잡고(같은 원인의 다른 구절은 여전히 놓치고) 있었다** — 이번에 근본 수정(공백
  정규화)으로 교체했다.
- **I-038**(신규 포함) — **스크립트 버그가 아니라 모집단 드리프트다.** I-038 블록에
  `execute_sql` 언급 문단이 **같은 회차(33일차) 안에서 BOARD가 29일차 DB CHECK
  재확인 절을 추가하며 새로 생겼다** — 이 문서가 처음 §1.2 스크립트를 돌린 시점엔 그
  문단이 없었다. 즉 **어느 스크립트의 문제도 아니고, §6이 이미 경고한 "모집단은 고정이
  아니다"가 같은 회차 안에서도 실제로 발생한 사례다**(아래 §6에 사례로 등재).

**CREW가 독립 실행에서 보고한 "25+9=34건"과의 관계**: CREW는 패치 **전** 스크립트(§1.2의
당시 버전, `실측\(SQL|rollback\)` 우회 분기 포함)를 그대로 복사해 돌려 34건을 얻었다 —
이 문서가 처음 적었던 33건과 1건(I-038) 차이였고, 그 1건은 위에서 설명한 드리프트였다.
**패치 후 스크립트(현재 버전)를 CREW가 재실행하면 이 35건이 나와야 한다** — 재현성의
기준을 "특정 정수와 일치"가 아니라 "이 스크립트를 실행하면 이 목록이 나온다"로 둔다(정수
자체를 외우게 하는 것보다 스크립트를 신뢰의 단위로 삼는 것이 다음 사람에게 더 안전하다).

**이 방법의 알려진 한계(정직 고지, 최초 버전에서 승계)**:

- **1단계(위 스크립트)는 기계적으로 재현 가능하다. 2단계(아래 §2 트리아지)는 아니다** —
  "화면 클레임이 있는가"는 정규식이 판단할 수 없어 사람이 각 블록을 읽고 정한다.
  **아래 §2가 그 판단 기준을 항목마다 명시한다** — "재현 불가능"을 감추지 않고, 대신
  "여기서부터는 사람 판단"이라는 경계선을 정직하게 긋는다(팀장이 제시한 두 갈래 중 (나)의
  요구를 (가)의 스크립트 위에 얹은 것 — 1단계는 (가), 2단계는 (나)의 정직성 원칙).
- **거짓 음성도 있다.** 브라우저 마커가 있다고 "그 판정 전체가 실렌더로 검증됐다"는
  뜻은 아니다 — 마커는 블록 어딘가에 그 단어가 있다는 것만 보장한다. 이번 회차는 이
  방향의 오탐은 별도로 감사하지 않았다 — 다음 사람이 검증할 과제로 남긴다.

## 2. 후보 35건 트리아지 — 화면 표시 여부로 걸러내기(판단 기준 명시)

### 4.1 순위 1(D-048)의 코드 레벨 재추적 — 완료(실렌더 아님)

`getMeetupById`(`src/lib/data/supabase/meetup.ts`)의 폴백을 실제로 부를 수 있는 소비자
전부를 grep으로 찾아(호출부 5곳: `MeetupDetailContainer`·`MeetupRescheduleContainer`·

필드(`title`/`date`/`place`/`pollId`/`status`)를 읽기 **전에** 활성 멤버십 확인이 선행하는지
코드를 직접 읽어 대조했다:

- **5곳 전부 안전하다** — 공통 불변식: `meetups_select_members` RLS는 "요청자가 그 크루의
  활성 멤버"일 때만 direct select를 허용한다. 즉 **폴백이 만들어지는 시점(direct select

  통과시키므로, 플레이스홀더가 화면까지 새는 경로가 코드상 없다.

## 5. 실렌더 확인 방법 — 다음 사람을 위한 고정 절차

32일차 BOARD의 실측 절차를 그대로 표준화한다(팀장 지시):

1. **접근성 스냅샷만 믿지 않는다.** `browser_snapshot`은 보조기술이 해석한 결과다 —
   "에러 로그 없음"이 "정상 렌더"를 의미하지 않는다(BOARD가 32일차에 실제로 이 함정을

2. **DOM을 직접 조회한다.** `browser_evaluate`로 대상 요소를 직접 골라 `style`·
   `textContent`·`getAttribute` 등 **원시 값**을 읽는다. 색이라면 `style` 인라인 변수
   (`--crew-color` 등)를, 문구라면 `textContent`를 그대로 대조한다 — 32일차 BOARD가
   `style="--crew-color:var(--crew-1);..."`를 직접 읽어 I-158을 확증한 것과 같은 수준.
3. **시나리오는 스크래치 픽스처로 재현하고 즉시 정리한다.** 기존 픽스처 크루를 건드리지
   않고 임시 UUID로 크루·멤버십·초대 등을 만들어 재현한 뒤, 확인 직후 삭제하고
   기준선(레코드 수)을 원복 확인한다(32일차 BOARD·CORE가 쓴 절차와 동일).
4. **판정 전/후(negative/positive) 둘 다 재현한다** 가능하면 — "이 조건에서 결함이
   있다"뿐 아니라 "이 조건이 아니면 정상이다"도 같이 확인해야 원인을 확정할 수 있다
   (I-124 26일차 실측이 이 원칙을 따랐다).
5. **결과는 원시 관측값을 그대로 기록한다** — "정상으로 보임" 같은 요약이 아니라
   `style="..."`·`textContent="..."` 같은 실제 값을 남긴다. 다음 사람이 재해석할 수
   있어야 한다.

### 7.5 방법론 메모 — `pg_depend`는 이 종류의 "누가 이 함수를 부르는가" 조사에 안 맞는다

CORE 교차검증(같은 회차) 중 팀장이 "함수 호출자 추적을 `pg_depend`로도 해보라"고
제안했는데, **실제로 돌려 보니 무효했다** — PL/pgSQL 함수 본문 안에서 다른 함수를
호출하는 것은 `pg_depend`에 구조적 의존성으로 기록되지 않는다(`pg_proc`을 `objid`로
걸어 조회하면 전혀 무관한 `pg_class` 참조만 나온다, 33일차 실측). **"어떤 함수가 어떤
함수를 호출하는가"를 SQL 카탈로그로 확인하려면 `prosrc`/`pg_get_functiondef` 텍스트를
정규식으로 뒤지는 것이 사실상 유일한 방법이다** — `pg_depend`는 컬럼 기본값·타입·확장
소속 같은 **구조적** 의존성만 추적하지, 함수 본문의 호출 관계는 다루지 않는다. 다음에
누군가 같은 종류의 "이 함수가 새 함수를 실제로 부르는가"를 확인하려 할 때 `pg_depend`를
다시 시도하지 않도록 여기 남긴다.

### 8.1 I-124 — forbidden 렌더 문구 4곳

**데이터 층에서 검증된 것**: 26일차 CREW가 REST+`begin`…`rollback`으로 "트리거 거부가

| 함수 | Server Action | UI 렌더 방식 |
| --- | --- | --- |
| `setCrewMembershipRole` | `set-crew-member-role.ts` | `!result.ok`면 **항상 고정 문구** `strings.crew.members.appoint.errors.failed`(코드 무관, `set-crew-member-role.ts:86-88`) |

(이번 회차에 새로 추가된 문구가 아니다), **렌더 코드 경로 자체도 이번에 새로 생긴 분기가

이미 있었다(예: 오너가 아닌데 강퇴를 시도하면 애초에 액션 앞단 권한 검사에서 같은

exception → DataResult로 바뀌는 지점"(데이터 층)뿐이고, 그 DataResult를 받은 뒤의 렌더
경로는 다른 원인의 forbidden과 100% 동일한 코드를 공유한다.** 즉 이론상 회귀 위험은
낮다 — 그러나 "이론상 낮다"와 "실제로 확인했다"는 다르므로 실렌더 대기로 남긴다.
**실렌더로 결판나는 지점**: 일반 크루원(staff/owner 아님) 세션으로 (i) 다른 사람의 role을
바꾸는 폼을 REST 우회 없이 **버튼으로** 제출 (ii) 남의 댓글 수정 시도 — 둘 다 지금은 UI
자체가 버튼을 안 보여줄 가능성이 높아(권한 없으면 폼이 렌더 안 됨) **REST 우회가 아니면
아예 트리거를 못 밟을 수도 있다** — 그렇다면 이 4곳은 "UI로는 재현 불가능한 방어선"이라
실렌더 감사의 대상 자체가 아니게 된다. **이 판별(버튼이 애초에 안 보이는가) 자체가 다음
확인 1순위**다.

### 9.1 후속(34일차) — Tier A가 "표시 층" 문제가 아니라 "기능 층" 결함을 끌어냈다

수가 항상 0으로 잡혀 poll이 즉시 닫힌다**(FR-041·D-022 직접 위반). 팀장이 정책 정의와
호출부를 직접 읽어 확인했다.

**이 절의 방법론이 왜 이걸 잡았는지 남긴다**: §9는 애초에 "SQL 진실값 ↔ 화면 렌더 대조"

매긴 것과 같은 이유로, "표시가 맞다"를 확인하려던 실행이 그 표시가 기대는 **조회 자체의
결함**을 함께 드러냈다. 33일차 워크로그가 "열려 있는데 아무도 안 본 축"을 다음 조사
방법으로 지목했는데, 이번엔 그 반대 방향 — **이미 판 축(표시 층 검증)이 그 밑의 기능 층을
물고 올라온 사례**다.

**같은 회차(34일차) DESIGN이 배정 1에서 구조적으로 대칭인 `join_requests` 테이블을 확인한
결과는 정반대였다**(`display-layer-audit-34/README.md` §1.5.5) — `join_requests_select_
requester_or_staff`는 같은 "본인 OR staff/owner" 형태지만 `crew_id IN (...)`으로 **크루
단위**로 걸려 있어 staff/owner 세션이 그 크루의 행 전체를 읽고, 실제로 role별 개수 비대칭이
없음을 실측으로 확인했다. **같은 정책 형태(self-or-staff)가 한쪽(poll)에서는 "투표자 본인
세션으로 집계를 센다"는 소비 방식과 결합해 결함이 되고, 다른 쪽(join_requests)에서는 "보는
사람이 애초에 staff/owner뿐"이라는 소비 방식과 결합해 결함이 안 된다** — RLS 정책 형태만
보고 판정하면 안 되고, 그 정책을 소비하는 코드가 **누구 세션으로, 무엇을 계산하는 데** 쓰는지
까지 봐야 한다는 것이 두 결과를 나란히 놓았을 때 드러나는 교훈이다. 다음 회차가 유사 패턴
(self-or-staff RLS + 집계·카운트 계산)을 더 찾을 때 이 두 사례를 대조 기준으로 쓸 수 있다.

**한 줄 더(팀장 지시)**: 이 축(Tier A)은 **33일차에 이 문서가 계획서로만 만들어 두고
아무도 실행하지 않은 항목**이었다 — §4.3·§9 본문에 "결론 없음, 다음 회차 착수점"으로
명시적으로 이월해 뒀다. 그 계획서를 34일차에 처음 집어 실행하자마자 (A) 결함이 나왔다 —
"계획서를 써 두는 것"과 "그걸 실제로 실행하는 것" 사이의 공백이 이번에도 방치 기간만큼의
위험을 그대로 담고 있었다는 뜻이다. CORE가 이번 회차 만들고 있는 "미착수 후속 항목 색인"이
존재해야 하는 이유가 이 사례 하나로 실증된다 — 계획만 있고 실행자가 배정되지 않은 축은
저절로 실행되지 않는다.
