# 열려 있는데 아무도 안 본 축 — 미착수 후속 항목 색인

**이 문서는 회차마다 갱신되는 살아있는 색인이다 — 파일명에 회차 번호를 붙이지 않는다.**
`docs/design/manual-verification-index/README.md`(33일차, 재실행 가능한 검증 절차의 색인)와
같은 성격이지만 대상이 다르다 — 저 문서는 "이미 완성된 절차를 다시 돌려야 하는가"를 찾고,
이 문서는 "닫힌 이슈·결정이 스스로 남긴 후속 작업 중 아직 아무도 손대지 않은 것"을 찾는다.

**왜 이 축인가(34일차 배정 근거)**: 33일차에 새로 판 SQL 축 3개(REVOKE·nested UPDATE·읽기/쓰기
게이팅)는 전부 "적용 불가" 또는 "추가 결함 0"으로 끝났다. 반면 팀장이 즉흥적으로 훑은
Mock/Supabase 계약 축(I-154가 열어 두고 아무도 안 훑은 자리)에서는 실제 결함(I-162)이
나왔다(`docs/prioritization-and-risks.md` I-162 처리 경위 참고). 결론: **새 축을 파는 것보다
"이미 열려 있는데 아무도 마저 안 본 축"을 훑는 쪽이 수확이 크다.**

## 0. 방법 — 어떻게 찾고 어떻게 셌는가

**측정 시각 기준(DESIGN 34일차 제안 채택)**: 이 문서의 숫자는 **`cb21e1c` + 워킹트리 dirty**
시점 기준이다 — 이 색인처럼 수시로 갱신되는 문서는 "지금 이 저장소 상태"와 "숫자를 셌던
시점"이 자연히 벌어진다(회차 중 다른 팀원의 커밋되지 않은 편집이 계속 쌓인다). 다음
검증자는 `git rev-parse --short HEAD` + `git status --porcelain`으로 지금 상태가 위 기준과
같은지부터 확인하고, 다르면 §0의 절차(전수 스캔 스크립트 재실행)를 다시 돌린 뒤 이 절의
기준을 갱신한다 — 숫자만 고치고 기준을 안 갱신하면 다음 사람이 또 같은 혼동을 겪는다.

**1차 추출(3개 병렬 조사, 전수)**: `docs/ISSUES.md`(원 색인 작성 시점 7,723행 — 위 측정
기준 갱신 시점 **7,827행**, +104는 그사이 쌓인 미커밋 편집분과 일치) 전체·`docs/decisions/*.md`
(**56개 파일**, `ls docs/decisions/*.md | wc -l`로 확인) 전체·`docs/prioritization-and-risks.md`
(3,200행) 전체를 각각 별도 조사로 완독시켜 "후속 후보"·"재검토 조건"·"다음 과제"·"다음에 그
파일을 만질 때"·"별도 결정으로 분리"·"향후"·"차후"·"추후"·"다음 회차" 류 표현이 가리키는,
**아직 실행되지 않은** 미래 작업을 원문 인용과 함께 뽑았다. 원시 인용 합계는 세 조사에서
약 180건(중복·같은 이슈의 여러 문단 포함).

**2차 대조(직접 수행, 근거 확보)**: 1차 추출을 그대로 믿지 않았다 — 실제로 아래 §0.1에서
서술하듯 **1차 추출이 "미완료"로 표시한 항목 중 다수가 코드·마이그레이션 실물 대조에서 이미
완료로 확인됐다.** 그래서 다음 순서로 대조했다:

1. `docs/ISSUES.md`의 `### I-NNN` 헤딩과 그 직후 `- **상태**:` 줄을 파이썬 스크립트로
   전수 파싱해 **162개 이슈의 현재 상태를 기계적으로 뽑았다**(사람이 눈으로 스크롤하며 세지
   않았다 — 33일차 CORE 자신의 두 번의 열거 오류가 "조사가 아니라 옮겨 적는 단계"에서
   났다는 진단에 따른 것이다). 스크립트는 이 문서 갱신 시 다시 실행 가능하다:
   ```python
   import re
   text = open('docs/ISSUES.md', encoding='utf-8').read()
   issues = {}
   cur = None
   for line in text.split('\n'):
       m = re.match(r'^### (I-\d+)', line)
       if m: cur = m.group(1); issues[cur] = {'status': None}; continue
       if cur and issues[cur]['status'] is None:
           m2 = re.match(r'^- \*\*상태\*\*:\s*(.*)', line)
           if m2: issues[cur]['status'] = m2.group(1)
   ```
2. **"열림" 상태인 이슈 29건**(원 색인 작성 시점 — 34일차 재실측 기준은 **28건**, §1 "바뀐
   것과 안 바뀌는 것" 참고)을 진짜 미착수 후보의 1차 모집단으로 삼았다 — ISSUES.md의
   상태 필드가 CLAUDE.md가 지정한 단일 소스이기 때문이다.
3. `docs/decisions/*.md`·`docs/prioritization-and-risks.md`에만 있고 어떤 `I-NNN`에도
   매핑되지 않는 후속 포인터는 **가능한 만큼 코드·마이그레이션 파일을 직접 grep해 실물
   대조**했다(§4). 전수는 아니다 — §4.3에 미검증 잔여를 정직하게 남긴다.
4. 판정이 애매한 항목은 33일차 선례(수동 검증 색인 §4)를 따라 **넣지도 빼지도 않고 이유와
   함께 별도 절(§5)에 남겼다.**

### 0.1 대조 과정에서 잡은 것 — 1차 추출을 그대로 옮기면 안 되는 이유

- **`I-096` 헤딩 자체가 파일에서 사라져 있었다.** `### I-096 · ...`의 첫 줄이 과거 커밋
  (`a130e09`, I-095 24일차 갱신 편집 중 충돌)에서 실수로 지워지고 제목 둘째 줄("않아
  `disband_crew`(FR-013 AC1)의...")만 본문에 고아로 남아 있었다 — `grep "^### I-"`로는
  안 잡히고 `grep "I-096"`(본문 참조)으로만 존재가 드러나는 상태였다. `git log -p -S"###
  I-096"`으로 원 제목을 복원해 헤딩을 되살렸다(이번 회차에 직접 수정 — 기존 번호가 있는
  블록 내용 수정은 D-082가 허용한다). **이 결번은 I-116(의도적 결번, ISSUES.md 자체 명시)과
  다르다** — I-116은 문서화된 의도, I-096은 순수 편집 사고였다. 복구 전/후 `### I-` 헤딩
  수: 162 → 163(템플릿 예시 `I-001`을 포함하면 163, 실제 이슈는 여전히 162 — `I-096` 복원
  +1, `I-116` 결번 그대로).
- **`rls-policies-029b.md` §11(범위 밖 이월 목록) 7건 중 5건이 이미 해결돼 있었다** —
  문서 자체는 갱신되지 않았지만 후속 Task(038·040·033) 커밋이 실제로 처리했다. 1차 추출은
  "이 문서 안에 완료 근거 없음"만 보고 미착수로 표시했는데, **코드(`recordAuditLog`,
  `remove-crew-member.ts` 주석)와 마이그레이션 파일명을 직접 열어보니 5건 중 4건은 이미
  구현돼 있었다**(§4.1). 이게 이 색인 전체의 방법론 교훈이다: **"이 문서 안에 완료 근거가
  없다"는 "미완료"와 동의어가 아니다** — 이 프로젝트는 이월 목록을 사후에 되짚어 고치지
  않는 append-only 문서 관행이라, 완료 근거는 다른 파일(구현 코드·후속 Task 문서)에만
  남는다. **그래서 이 색인은 문서 인용만으로 "미착수"를 확정하지 않고, 확인 가능한 것은
  전부 코드·마이그레이션 실물을 grep했다.**

## 2. 미착수 상위 랭킹 — "실제 미확인 결함이 있을 사전 확률" 순

**등급(영향도) 순이 아니다.** 33일차 DESIGN이 쓴 기준(반복 관찰·검증된 방법론 존재·시스템
전반에 영향을 미칠 잠재력)을 그대로 따랐고, 이 기준의 자의성 없음은 33일차 CREW 교차검증이
이미 확인했다. 순위 뒤 괄호는 근거 한 줄이다.

1. ~~**`crews_update_staff_or_owner`의 archived 방어 defense-in-depth 미확인**(I-066 잔여
   범위)~~ — **해소(35일차, CREW → BOARD 교차검증 → 팀장 조건부 승인 → 적용).** 실측
   (`begin…rollback` + 실 JWT claims)으로 "RLS는 archived를 전혀 안 보고 방어는 트리거 단일
   지점뿐"임을 확정했다. 1차 결론("이중화 전면 불필요")은 리뷰 짝 BOARD 교차검증 + 팀장
   반론으로 정정됐다 — 나이브 전면 이중화는 `forbidden`→`not_found` 오류 열화라는 상시
   비용이 실측으로 드러나 기각했지만, **WITH CHECK 전용 좁은 이중화**(`USING`은 원본 유지)는
   오늘 비용 0 + 트리거 회귀 시 즉시·자동 방어(`42501`)를 실측으로 확인해 채택을 제안했다.
   BOARD가 독립 스크립트로 같은 결과를 재현하고(4/4 pass) 팀장이 조건부(BOARD 통과 → 무결성
   감사 통과 → 회귀 3종 확인) 승인했다 — 마이그레이션 `20260731025523_crews_update_staff_or_
   owner_archived_with_check_backstop_i066.sql`을 적용하고, `audit_compare.py`로 134/134·
   불일치 20건 그대로(신규 0건)를 확인했으며, 적용 후 회귀 3종(archived 편집 여전히
   `P0001`·활성 크루 편집 정상·`updateCrewInfo` 여전히 `forbidden`) 전부 실측 PASS했다.
   상세: `docs/design/crews-archived-defense-35/README.md`,
   `rls-regression-checklist-33/README.md` §7.
2. **Turbopack·WSL drvfs 클러스터**(I-048·I-135·I-139 — 4회+ 독립 관찰, 정확한 유발
   조건은 여전히 미확보) — 이 자체가 결함일 뿐 아니라, 이 프로젝트 전체가 "브라우저·dev
   서버로 직접 확인"에 크게 의존하는데 그 확인 도구 자체의 신뢰성이 흔들린다는 **배율
   리스크**다. 근본 원인이 안 잡히는 한 다른 모든 실측 결과에 "어쩌면 캐시 문제였을 수도"
   라는 그림자가 남는다.
3. **I-052 · 인증 보호 라우트의 소프트 404(HTTP 200)** — 설계 결정(D-040) 자체가 8일차부터
   보류 상태로 방치돼 있다. 모니터링·검색엔진·API 소비자 관점에서 실제로 관측 가능한 차이
   (200 vs 404)이며, 결정이 하나도 안 났다는 것 자체가 "아무도 마저 안 본" 상태의 정의에
   부합한다.
4. **I-057 · 비밀번호 재설정 PKCE 템플릿 미확인** — FR-003 핵심 인증 플로우가 **한 번도
   end-to-end로 검증되지 않았다.** 외부 의존(수신 링크 확보)이 막고 있을 뿐 코드는 이미
   결정을 내려 배포된 상태라, 링크가 잘못되면 사용자가 비밀번호를 재설정할 수 없는 채로
   운영에 들어간다 — 발견 즉시 판정 가능하도록 절차는 이미 완성돼 있다(`docs/decisions/
   i057-password-reset-template-verification.md`).
5. **I-056 · 탈퇴 계정 파기가 Admin API가 아니라 `postgres` role의 직접 SQL로 `auth.users`를
   수정한다** — PII(이메일) 처리 경로가 공식 API 계약 밖에 있다. 지금까지는 동작하지만
   Supabase가 `auth.users` 스키마를 바꾸면(내부 스키마라 공지 없이 바뀔 수 있음) 조용히

## 7. 이 색인을 최신으로 유지하는 규칙

1. **새 결정·이슈 문서를 닫으면서 "후속 후보"·"재검토 조건"류 표현을 남기는 사람은 그
   표현이 §3(이미 `I-NNN`이 있는 경우) 또는 §4(없는 경우)의 표에 들어갈 후보인지 스스로
   먼저 판단한다.** 다만 매 회차 이 문서를 통째로 다시 쓰지는 않는다 — §0의 방법(3파일
   전수 스캔)은 **새로 추가된 문서·새로 "열림"이 된 이슈만 대상으로 반복**하면 된다.
2. **"미완료"로 보이는 문서 인용을 그대로 옮기지 않는다** — §0.1이 증명했듯 이 프로젝트의
   append-only 문서 관행 때문에 문서 내부 서술과 코드 실물이 어긋나는 경우가 흔하다. 표에
   새 행을 추가하기 전에 관련 코드·마이그레이션을 최소 한 번은 grep한다.
3. **숫자를 고칠 때는 표를 다시 세어 §1 요약과 맞춘다.** 세는 방법(§0의 파이썬 스크립트,
   `git log -p -S` 대조, `grep -c`)을 함께 남긴다 — 33일차에 이 규율이 없어서 CORE 자신이
   두 번 숫자를 틀렸다.
4. **판단이 갈리는 항목은 §5에 남기고 억지로 분류하지 않는다.**
5. **이 색인에서 항목을 빼야 할 때는 삭제하지 않고 취소선 + 제외 사유로 보존한다** — 이
   프로젝트는 append-only 문서 관행을 쓰고(§0.1), 이 문서 자체의 존재 이유가 회차 간 델타
   대조이므로 흔적 없이 지우면 다음 검증자가 "왜 빠졌는지"를 알 수 없다(34일차 DESIGN
   교차검증이 §1·§3의 이 규약 부재로 실제 오독을 겪은 뒤 정한 규칙). **다만 집계(숫자
   요약·버킷 합)는 취소선 처리된 행을 반드시 제외하고 센다** — 이 두 번째 문장을 빼면
   다음 사람이 취소선 행까지 세어 총건수를 다시 틀린다.
