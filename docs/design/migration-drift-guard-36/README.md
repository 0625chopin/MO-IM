# 마이그레이션 존재·이름 드리프트 실측 (36일차, CORE)

I-051(`mcp__supabase__apply_migration`이 원격에만 적용하고 로컬 파일을 만들지 않는다) 후속
배정 — 미착수 후속 항목 색인(`docs/design/unexplored-followups-index/README.md` §2 랭킹
7위)의 근거: "재발 방지가 '규약으로 남긴다'는 절차 문서뿐이고 자동 검증(예: 원격·로컬 버전
diff 스크립트)은 없다 — 세 번째 사고가 날 때까지 그대로일 구조다." 실제로는 17·19·27일차
세 번 발생했다.

35일차에 CORE 본인이 만든 `docs/design/migration-integrity-audit-35/audit_compare.py`가
출발점이다. 그 스크립트는 **내용**(I-167·I-168 축 — 같은 버전 키에 대해 로컬 파일과 원격
`statements`가 바이트 단위로 같은가)을 감사한다. 이 문서는 그 옆에 있는, I-051이 실제로
걸렸던 **존재·이름** 축을 감사한다.

---

## 1. 드리프트 세 종류와 정의

배정된 정의 그대로다:

- **(a)** 원격에만 있고 로컬 파일이 없음 — "로컬 파일 누락"
- **(b)** 로컬에만 있고 원격에 없음 — "원격 미적용"
- **(c)** 양쪽에 다 있으나 파일명 버전 접두어가 원격 `version`과 불일치 — "파일명 오기재"
  (27일차 CORE 본인의 실제 사례: 원격 version 대신 회차 시각 기준 임의값을 파일명에 씀)

**I-168(35일차, 사후 편집 20건)과의 구분**: I-168은 버전 키가 같은 파일/행 사이의 **내용**
차이(주석·SQL 문구 편집)를 다룬다. 이 문서가 다루는 세 축은 **파일 존재 여부와 파일명**만
본다 — 내용은 전혀 보지 않는다. 서로 다른 축이라 숫자를 합산하지 않는다.

## 2. `audit_compare.py`의 커버 범위 판정(코드 근거)

`docs/design/migration-integrity-audit-35/audit_compare.py`를 읽고 판정했다.

| 축 | 판정 | 근거 |
| --- | --- | --- |
| (a) 원격에만 있음 | **잡는다** | `only_remote = sorted(remote_versions - local_versions)`(109행), 불일치 시 "원격에만 있음(로컬 파일 누락)"으로 출력(113행) |
| (b) 로컬에만 있음 | **잡는다** | `only_local = sorted(local_versions - remote_versions)`(108행), 불일치 시 "로컬에만 있음(원격 미적용 — I-051 패턴 의심)"으로 출력(111행) — 스크립트 자체가 이 축을 I-051로 명명하고 있다 |
| (c) 파일명 버전 접두어 불일치 | **못 잡는다** | `load_local`(59행)이 `versions = [fn.split("_")[0] for fn in filenames]`(64행)로 **파일명 앞 14자리를 그대로 신뢰**해 로컬 버전 키로 쓴다. 파일명이 잘못 붙어 있으면 그 잘못된 문자열이 곧 "로컬 버전"이 되어 원격의 진짜 버전과 절대 매칭되지 않는다 — **매칭 실패는 나지만, "같은 마이그레이션의 이름이 잘못 붙었다"는 정보가 사라지고 (a) 1건 + (b) 1건, 서로 무관한 두 개의 가짜 경보로 갈라져 나온다.** |

**왜 이게 문제인가**: 27일차 실제 사고를 그대로 넣어 보면(§4 합성 테스트가 이 시나리오를
재현한다) `audit_compare.py`는 "원격에 어떤 버전이 로컬에 없다"와 "로컬에 어떤 버전이
원격에 없다"를 각각 독립적으로 보고한다. 사람이 두 목록을 눈으로 대조해 "어? 이 두 개가
사실 같은 파일 아닌가?"를 알아채야만 (c)를 (a)+(b)로 오인하지 않는다 — 27일차에 실제로
팀장이 육안으로 대조해서만 잡아냈다(I-051 27일차 블록 참고). **자동화가 없다는 이 색인의
지적이 정확히 이 지점을 가리킨다.**

## 3. 확장 — `drift_check.py`

`docs/design/migration-drift-guard-36/drift_check.py`를 신설했다(`audit_compare.py`를
그대로 고치지 않고 옆에 둔 이유는 §5 참고).

**핵심 아이디어**: 원격 `schema_migrations.name` 컬럼과 로컬 파일명의 "버전 접두어 뒤
부분"을 **이름 기준으로 교차 매칭**한다. (a) 후보(원격에만 있는 버전)와 (b) 후보(로컬에만
있는 버전) 중 이름이 같은 쌍이 있으면 "같은 마이그레이션인데 로컬 파일명 버전 접두어만
잘못됐다"로 판정해 (c)로 재분류한다. 이름까지 우연히 같은 후보가 여러 건이면(모호) 자동
재분류하지 않고 사람 확인 항목으로 따로 보고한다 — 오매칭보다 미탐(사람에게 넘기는 것)이
안전하다는 판단이다.

전제: Supabase CLI/`apply_migration`이 기록하는 `name`이 로컬 파일명 규칙
(`<version>_<name>.sql`)의 이름 부분과 같다 — 이번 회차 실측 134건 전부에서 그렇다는 것을
확인했다(§4 데이터).

### 3.1 합성 데이터로 (c) 탐지를 검증

실제 저장소에 현재 (c) 사례가 없어서(§4), **탐지 로직 자체가 동작하는지**는 합성 데이터로
따로 검증했다:

```
로컬: 20260725085454_..., 20260730090000_join_requests_guard_archived_crew_decision_31.sql(버전 오기재), 20260724103449_...
원격: 20260725085454(match), 20260730071317/join_requests_guard_archived_crew_decision_31(진짜 버전), 20260724103449(match), 20260731999999/only_on_remote_missing_local_file(로컬 없음)

결과:
(a) 1건 — 20260731999999 only_on_remote_missing_local_file
(b) 0건
(c) 1건 — 로컬 20260730090000_join_requests_guard_archived_crew_decision_31.sql ↔ 원격 20260730071317
```

`audit_compare.py` 방식이었다면 이 시나리오는 (a) 2건("20260731999999"·"20260730071317")
+ (b) 1건("20260730090000_...")으로, **실제로는 1건인 (c)가 (a)+(b) 3개의 무관한 항목으로
쪼개져 나왔을 것**이다. `drift_check.py`는 이를 정확히 (c) 1건 + 진짜 (a) 1건으로 분리했다
— 확장이 실제로 의도한 축을 잡는다.

## 4. 실측 — 현재 저장소 상태(2026-07-31, 36일차)

- 원격: `select version, name from supabase_migrations.schema_migrations order by version`
  — **134행**
- 로컬: `supabase/migrations/*.sql` — **134파일**
- `drift_check.py --remote-json remote_versions.json --migrations-dir ../../../supabase/migrations` 실행 결과:

```
원격 행 수: 134
로컬 파일 수: 134
버전 일치(양쪽에 같은 버전 존재): 134

=== (a) 원격에만 있음 — 로컬 파일 누락 ===
  0건

=== (b) 로컬에만 있음 — 원격 미적용 ===
  0건

=== (c) 양쪽에 다 있으나 파일명 버전 접두어가 원격 version과 불일치 ===
  0건

요약: (a)=0건 (b)=0건 (c)=0건 모호=0건
```

**세 축 모두 0건.** 134개 버전이 원격·로컬 양쪽에 정확히 같은 집합으로 존재하고, 이름
교차 매칭이 필요한 사례(즉 애초에 버전 접두어가 어긋난 파일) 자체가 없다 — 34~35일차
CORE·DESIGN·BOARD의 반복된 대조·rename 작업(I-051 19일차 후속·27일차 후속)이 누적돼 현재는
이 축의 드리프트가 완전히 해소된 상태로 보인다. `remote_versions.json`을 이 디렉터리에
남겨 재현 가능하게 했다.

**재실행 절차**:
1. `mcp__supabase__execute_sql`로
   `select json_agg(json_build_object('version', version, 'name', name) order by version) as data from supabase_migrations.schema_migrations;` 실행
2. 결과의 `data` 배열을 `remote_versions.json`으로 저장(`[{"version":...,"name":...}, ...]`)
3. `python3 drift_check.py --remote-json remote_versions.json --migrations-dir ../../../supabase/migrations`

### 4.1 재검증(2026-07-31, 36일차 마감 — 이 도구가 회차 안에서 실제로 쓰인 첫 사례)

같은 회차 안에 마이그레이션 2건이 새로 적용됐다 — CREW(`20260731034803_fix_anonymize_
expired_deactivated_profiles_handle_083_conflict`, (A)급 PII 파기 수정)와 BOARD
(`20260731034928_chat_messages_insert_type_gate_i063`, I-063 WITH CHECK 게이트). §4의
134건 스냅샷은 이제 낡았으므로 `remote_versions.json`을 다시 뽑아 전 과정을 재실행했다.

**존재·이름 축(`drift_check.py`)**: 원격 136행, 로컬 136파일 — (a)=0건 (b)=0건 (c)=0건,
모호 0건. 신규 2건 포함 세 축 전부 여전히 0.

**바이트 대조(신규 2건 한정)**: 로컬 `wc -c` vs 원격
`octet_length(array_to_string(statements, E'\n'))`.

| 버전 | 로컬 `wc -c` | 원격 `octet_length` | 일치 |
| --- | --- | --- | --- |
| `20260731034803`(CREW) | 2260 | 2260 | ✅ |
| `20260731034928`(BOARD) | 1131 | 1131 | ✅ |

둘 다 정확히 일치 — 사후 편집 없이 원격 원문 그대로 로컬에 반영됐다.

**내용 축(`audit_compare.py`, I-167·I-168 — 별개 축, 혼동 방지 위해 여기서도 명시)**:
원격 `statements[1]` 전체 덤프(136행, 45만자 초과로 도구가 자동 파일 저장 →
`--raw-tool-output`으로 대조)로 재실행. 결과: **136=136, 내용 일치 116건, 불일치
20건 — I-168이 이미 알고 있던 바로 그 20건과 정확히 같은 버전·같은 MD5**(예:
`20260724104430`의 local_md5=`cc633a...`·remote_md5=`c74e5e...`가 35일차 문서 표와 바이트
단위로 동일). **신규 2건(`20260731034803`·`20260731034928`) 둘 다 불일치 목록에 없다 —
신규 불일치 0건, 이번 판정 기준을 통과했다.** 기존 20건의 실측 전문·정규화 규칙은
`docs/design/migration-integrity-audit-35/README.md`가 단일 소스이고 여기서는 재론하지
않는다.

**결론**: 이번 회차에 새로 만들어진 도구(§3 `drift_check.py`)가 같은 회차 안에서 실제로
쓰인 첫 사례이며, 존재·이름·바이트·내용 네 겹의 대조 전부 신규 마이그레이션 2건에 대해
드리프트 0건을 확인했다.

## 5. `audit_compare.py`를 직접 고치지 않고 옆에 둔 이유

`audit_compare.py`는 I-167 전용으로 설계된 **내용** 감사 도구다(원격 `statements` 전문이
필요하고, 이는 134건 전부를 받으면 토큰 비용이 크다 — 35일차 문서가 "45만자 초과, 도구가
자동 파일 저장"이라고 기록한 그 비용이다). 이번에 필요한 **존재·이름** 축은 `version`·
`name` 두 컬럼만 있으면 충분해 훨씬 가볍다(이번 회차 실측은 SQL 1줄로 끝났다). 두 축을 한
스크립트에 합치면 가벼운 검증(회차 마감 전 매번 돌리고 싶은 것)이 무거운 덤프(수동으로만
가끔 돌리는 것)에 종속돼 실행 빈도가 떨어질 위험이 있다고 판단해 **별도 스크립트로
분리**했다. 대신 두 스크립트가 서로의 커버 범위를 이 문서(§2)와 `audit_compare.py`
자신의 docstring(35일차 원문 그대로 유지, 신규 언급 없음)에 명시해 "어느 스크립트가 뭘
보는지" 혼동을 없앴다. 향후 실제로 병합이 이득이라고 판단되면(예: 매 회차 두 스크립트를
항상 같이 돌리는 게 관행이 된다면) 이 판단을 재검토할 수 있다 — 지금은 분리가 더 싸다는
판단이다.

## 6. 팀 표준(27일차 3줄) 승격 여부

I-051 27일차 블록이 남긴 "팀 표준 제안 3줄"을 `docs/CONVENTIONS.md`에 넣을지는 원래
I-140과 함께 결정하기로 돼 있었다. 확인 결과:

- **I-140은 해결됨(28일차)**이지만, 그 결정은 **`ISSUES.md`·`prioritization-and-risks.md`
  동시편집·번호 부여 규칙**(D-082)에 관한 것이었다 — I-051의 "마이그레이션 절차 3줄"에는
  직접 답하지 않는다. 다만 **그 결정이 세운 원칙은 그대로 적용된다**: D-082는 "회차 운영
  절차이므로 `docs/CONVENTIONS.md`엔 참조 한 줄만 남기고 본문은 `team-day-runner/SKILL.md`
  §0-1에 둔다"고 명시했고, `docs/CONVENTIONS.md` 250~253행이 그 참조 한 줄로 실제
  존재한다("코드 디렉터리·명명 규약이 아니라 회차 운영 절차이므로 ... 두 곳에 중복
  등재하지 않는다").
- I-051의 3줄도 코드 디렉터리·명명 규약이 아니라 **MCP 도구(`apply_migration`) 사용 시
  지키는 회차 운영 절차**라는 점에서 같은 범주다. **같은 원칙을 일관 적용하면
  CONVENTIONS.md 본문 승격은 부적합하다고 판단한다.**
- 대신 이번에 만든 자동 검증(§3~§4)이 "사람이 3줄을 기억한다"보다 강한 방어선이다 —
  `docs/design/manual-verification-index/README.md`에 등재해 매 회차 마감 전 실행을
  권장했다(아래 §7).
- 이 판단과 "CONVENTIONS.md에 참조 한 줄만은 남길지" 여부는
  `docs/DECISIONS.draft.CORE.md`에 번호 없이 제안했다 — **CONVENTIONS.md는 직접 고치지
  않았다**(팀장 승인 사항).

## 9. 미검증 잔여

- `drift_check.py`의 이름 교차 매칭은 원격 `name`이 로컬 파일명 규칙과 항상 일치한다는

  아니라 다른 경로로 적용해 `name`이 비거나 다른 규칙을 따른다면 이름 매칭이 조용히
  실패할 수 있다(이 경우 (c)로 재분류되지 않고 (a)+(b)로 그대로 보고되므로 **안전한
  방향의 실패**다 — 놓치는 게 아니라 더 눈에 띄게 보고된다).

  필요하다 — §7 등재로 "언제 돌리는가"는 명시했지만 실제 실행은 여전히 사람이 기억해야
  한다(이 프로젝트 전체가 R-002로 CI가 없어 안고 있는 공통 한계).
