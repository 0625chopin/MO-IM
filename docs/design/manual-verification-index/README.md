# 수동 검증 절차 색인 (Manual Verification Index)

**이 문서는 회차마다 갱신되는 살아있는 색인이다 — 파일명에 회차 번호를 붙이지 않는다.** CI가
아직 없어서(R-002, `docs/prioritization-and-risks.md`) 이 프로젝트의 회귀 방어 상당수는
"사람이 문서의 존재를 기억하고 다시 돌리는 것"에 전적으로 걸려 있다. 문서가 늘어나는 속도보다
색인이 늦으면 회차가 쌓일수록 체크리스트는 늘고 실행률은 0으로 수렴한다 — 이 문서는 그 수렴을
막기 위한 것이다.

**이 문서는 내용을 복제하지 않는다.** 각 절차의 SQL·curl·판정 기준의 단일 소스는 원 문서다.
여기서는 **무엇을 보장하는지·언제 돌리는지·얼마나 걸리는지·CI로 옮길 수 있는지**만 요약하고
원 문서 경로(및 절)를 가리킨다. 건수·날짜 같은 갱신 값은 이 문서 안에서만 쓴다(다른 문서에
복제하지 않는다, CLAUDE.md 단일 소스 원칙).

## 0. 어떻게 찾았는가 (33일차 최초 작성)

`docs/design/**/*.md`(11개)·`docs/decisions/*.md`(56개) 전수 67개 파일을 스캔했다. 방법:
① 파일명·헤딩으로 "감사(audit)"·"검증(verification)" 부류 선별 ② 본문에서 `체크리스트`·
`재현 절차`·`확인 방법`·`판정 기준`·`curl`·`begin;`·`언제`·`도착 즉시` 등 신호어를 grep ③
신호어가 걸린 파일은 해당 절을 읽어 "**사람이 나중에 다시 실행해야 하는, 기대 출력이 있는
재현 가능한 절차**"인지 "**이미 종결된 1회성 조사 로그**"인지 판별. 신호어가 안 걸렸어도
파일명이 감사류인 것(`i032-tone-check-29` 등)은 직접 읽어 확인했다. 판별 기준은 "이 문서가
없어지면 다음에 같은 걸 다시 확인할 방법이 없어지는가"였다.

**결과(33일차 원문 그대로 보존)**: 재사용 가능한 검증 절차 **19개 파일 · 20개 절차**(하나는
파일 안에 절차 2개), 해당 없음(종결된 조사 로그·순수 결정 기록) **48개 파일**, 판단이 갈릴
수 있어 불확실로 남긴 것 **3개 파일**(§4). 전수 목록·판별 근거는 이 문서 갱신 시 재확인할
때 처음부터 다시 훑는 대신, 아래 표에 없는 새 후보만 추가로 검토하면 된다(§5).

**정정(36일차, CORE — DESIGN 교차검증으로 발견)**: 위 "하나는 파일 안에 절차 2개"는 **33일차
최초 작성 때부터 이미 틀린 전제였다.** 실제로는 **둘**이다 — `chat-retention-035.md`(§7·§8)와
`c-half-confirmed-31.md`(§1·§2)가 각각 절차 2개씩을 가지며, 둘 다 33일차 원본 표에 이미
있었다(이번 회차에 새로 생긴 게 아니다). 이 "하나뿐"이라는 잘못된 전제 때문에 §3의 CI 이관
분포(가능/부분/불가)가 33일차부터 실제 표 내용과 어긋난 채 35·36일차까지 그대로 상속됐다 —
매 회차 편집자가 "이전 요약값 + 1"로만 갱신하고 표 전체를 다시 세지 않았기 때문이다(§3 갱신
이력 참고). **파일 수**(19·20개로 적힌 숫자)는 결과적으로 우연히 맞았을 뿐이다 — "절차 2개인
파일이 하나뿐"이라는 축소 오류(-1)와 `permission-baseline-raw-27.md`(원 문서에 종속된 순수
원시 데이터 별첨, 그 자체로 판정 기준이 없다)를 별도 파일로 얹어 센 확대 오류(+1)가 33·35일차
모두에서 우연히 상쇄됐다. 36일차에 원시 데이터 별첨이 아닌 **진짜 새 파일**(`migration-
drift-guard-36/README.md`)이 추가되면서 이 상쇄가 처음으로 깨져 파일 수 오류가 겉으로
드러났다 — 즉 36일차의 "21개 파일" 오기재는 새로 만든 실수가 아니라, 3회차 동안 숨어 있던
정의 공백이 처음 노출된 것이다. **파일 수 집계 규칙을 이제 명시한다**: 각 절차 행의 첫
`docs/...` 경로를 그 행의 "파일"로 삼고, 같은 파일이 절차 여러 개를 나눠 가지면 1개로만
세며, 그 절차를 뒷받침하는 원시 데이터 별첨은 별도 파일로 세지 않는다. 이 규칙을 표 원문에서
기계적으로 재계산하는 스크립트를 `count_check.py`로 만들었다(§3 참고) — 사람이 손으로 다시
세지 않아도 된다.

  (CI 없음) 때문에 현재는 전부 수동 실행**이다. 이관 가능성과 실제 이관 여부는 별개다.
  **정정(36일차)**: 이전 버전들은 "부분 10~11 · 불가 5"로 적었다 — 이 오분포는 33일차
  최초 작성부터 있었고(§0 정정 단락 참고) 35·36일차 모두 "이전 값 + 1"로만 갱신하며
  재확인 없이 물려받았다. **36일차 BOARD 갱신**: 가능 6 → 7(신규 행이 "가능"으로 분류돼서
  — 순수 SQL이라 CI 이관 가능).
- **해당 없음(종결된 1회성 조사 로그·순수 결정 기록)**: 48개 파일 — 재실행 트리거가 없어 이
  색인에서 뺐다.
- **재검산 스크립트**: 위 세 숫자(파일 수·절차 수·CI 분포)는 이제 사람이 손으로 세지 않는다.
  `python3 docs/design/manual-verification-index/count_check.py`를 이 문서를 고칠 때마다

  세므로 "이전 값 + 1" 방식의 상속 오류가 구조적으로 재발하지 않는다.

## 5. 이 색인을 최신으로 유지하는 규칙 (제안 — 결정 승격 필요)

**규칙(제안)**: 새 수동 검증 절차 문서(재실행 트리거·기대 출력이 있는 체크리스트)를 만든
사람은 **같은 작업 안에서 이 문서에 표 한 줄을 추가한다** — 원 문서 경로, 한 줄 요약, 트리거
조건, 소요 시간, CI 이관 여부. 문서 갱신 없이 체크리스트만 늘리는 것은 §0이 우려하는
"실행률 0 수렴"을 그대로 재현한다.

이 규칙은 팀 운영 규칙이라 CORE 단독으로 확정하지 않는다 — 팀장 판단을 위해
`docs/DECISIONS.draft.CORE.md`에 번호 없이 제안해 뒀다.

**추가 규칙(제안, 33일차 팀장 관찰)**: **표를 고칠 때 도입문·요약절의 건수를 함께 갱신한다
— 같은 문서 안에서 같은 숫자가 두 곳(도입문 vs 표, 본문 vs 요약)에 따로 적혀 있으면 한쪽만
고치고 다른 쪽을 잊는 사고가 반드시 난다.** 33일차 하루에만 이 패턴으로 숫자가 어긋난 사례가
세 번 있었다(I-155 처분 문서의 "19개" vs 실제 23개, I-158 draft의 "15곳" vs 나열 19개, 그리고
이 색인 §1의 "4개" vs 표 3행) — **세 건 모두 판정 자체는 맞았고 숫자만 틀렸다.** 공통 원인은
조사 단계가 아니라 **문서에 옮겨 적는 단계에서 숫자를 손으로 다시 쓰며 어긋나는 것**이다.
그래서 같은 값을 여러 곳에 중복해서 적어야 하는 문서(도입문+표, 본문+요약절 등)를 쓸 때는
가능하면 한쪽이 다른 쪽을 "표를 보라"는 식으로 가리키게 하고, 부득이 중복해야 하면 **고칠 때
전수 grep으로 같은 숫자가 몇 곳에 더 있는지 확인한 뒤 전부 함께 고친다.**
