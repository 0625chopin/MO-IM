# 마이그레이션 무결성 전수 감사 (35일차, CORE)

I-167(34일차, 팀장 실측)이 미착수로 남긴 전수 감사다. I-167이 다룬 개별 사례
(`20260731010558`)는 이미 되돌림 + 정정 마이그레이션으로 해소됐지만, "현재 무결성 검증
(개수 대조 + version-only MD5)이 사후 편집을 구조적으로 탐지하지 못한다"는 결함 자체는
열려 있었다. 이 문서는 그 구조적 결함을 메울 **문장 단위 정규화 규칙**을 설계하고, 로컬
`supabase/migrations/*.sql` 133건 전부를 원격 `supabase_migrations.schema_migrations`와
**전건 대조**한 결과다.

## 0. 결과 요약

| 항목 | 값 |
| --- | --- |
| 로컬 마이그레이션 파일 | 133건 |
| 원격 `schema_migrations` 행 | 133건 |
| 버전 집합 일치(개수+version) | 일치 — **기존 검증은 여기서 "이상 없음"으로 끝난다** |
| 내용 일치(아래 §2 정규화 적용 후) | **113건** |
| 내용 불일치 | **20건** — 이 중 17건 주석만, **3건은 실행되는 SQL/카탈로그 문자열 자체가 다르다** |
| 라이브 DB 기능 영향 | **0건** — 3건 전부 이후 정정 마이그레이션이 실제로 적용돼 있어 현재 배포 상태는 로컬 파일과 일치(§4) |

**기존 검증(개수 대조 + version-only MD5)은 이 20건 중 단 1건도 잡아내지 못했을 것이다.**
20건 중 최소 1건(`20260724104430`)은 I-167이 34일차에 이미 "확인"했다고 기록한 파일인데,
그 확인 자체가 "빈 `--` 구분줄 하나가 빠졌을 뿐"이라는 잘못된 진단이었다 — 실제로는
문단 전체가 다른 내용으로 바뀌어 있었다(§3.1). 즉 **이번 감사는 미착수 항목을 채운 것에
그치지 않고, I-167 자신의 대조군 진단 오류까지 정정한다.**

## 1. 방법 — 전건 확보

- 원격: `mcp__supabase__execute_sql`로
  `select json_agg(json_build_object('version', version, 'stmt', statements[1]) order by
  version) as data from supabase_migrations.schema_migrations` 1회 실행. 결과가 45만자를
  넘어 도구가 자동으로 파일 저장 → 그 파일에서 `<untrusted-data-...>` 마커 사이 JSON을
  파싱해 133행 전부 확보(표본 아님, `len(records) == 133` 확인).
- **`array_length(statements, 1)`을 133건 전부에서 먼저 확인했다 — 전부 정확히 1이다.**
  이 프로젝트에서는 `statements` 배열이 "문장 단위로 쪼갠 여러 원소"가 아니라 **그
  마이그레이션을 적용할 때 제출한 SQL 원문 전체가 배열의 유일한 원소**로 저장된다는
  뜻이다(추정 근거는 §5). 그래서 `statements[1]` 하나만 보면 그 마이그레이션의 전체
  기록을 다 보는 것이다 — 여러 원소를 순회할 필요가 없다.
- 로컬: `supabase/migrations/*.sql` 133개 파일 전부를 파일명의 버전(언더스코어 앞
  14자리)으로 키를 맞춰 읽었다.
- 버전 집합을 정렬해 diff했다 — **정확히 일치**(133=133, 양쪽에만 있는 버전 0건). 이건
  기존 절차(개수 대조)가 이미 하던 확인이고, 여기서도 통과한다 — **이 결과 자체가
  "내용까지 안전하다"를 보장하지 않는다는 것이 이 감사의 출발점**이다.
- **버전 접두어 중복 0건(35일차, BOARD 교차검증으로 재확인)**: 로컬 133개 파일명의 앞
  14자리를 키로 dict를 만드는 방식(§6 `audit_compare.py`의 `load_local`)은, 만약 서로
  다른 두 파일이 같은 버전 접두어를 갖는다면 뒤에 읽은 파일이 앞 파일을 조용히 덮어써
  그 파일 하나가 대조에서 통째로 빠지는 함정이 있다 — I-051류(도구가 로컬 파일을 안
  만드는 것 자체는 아니지만, "버전이 키인데 그 키가 유일하다고 가정한다"는 성격이 같다)
  함정이다. 133개 파일명을 14자리로 잘라 집합 크기를 세어 **원본 리스트 길이(133)와
  정확히 일치함을 확인했다** — 중복 0건, 이 함정은 이번 데이터셋에는 없었다.

## 2. 정규화 규칙 — 설계와 근거

### 2.1 시도했다가 기각한 규칙: 주석 줄 제거

I-167은 "문장 단위로 정규화(주석 포맷·줄바꿈 차이를 흡수)해야 한다"고 제안했다. 처음에는
`--`로 시작하는 줄과 빈 줄을 양쪽에서 전부 제거한 뒤 비교하는 규칙을 시도했다. **이
규칙으로 31건의 whole-file 불일치 중 17건이 "코드는 완전히 같고 주석만 다르다"로 분류됐다
— 그래서 처음엔 이걸 "안전한 정규화 규칙"으로 채택하려 했다.**

**기각한 이유**: 나머지 3건(§4)에서 정확히 같은 위치(주석/코드 경계)에 **의미가 다른
실제 SQL**(문자열 리터럴 값이 다른 `comment on function/column`, 컬럼 한정자가 다른
`where` 절)이 숨어 있었다. 이 3건을 역추적한 결과 **주석이 사라진 17건도 "저장 과정의
정규화"가 아니라 "적용 후 로컬 파일에 설명 주석을 추가하고 다시 마이그레이션을 돌리지
않은" 같은 종류의 사후 편집**이라는 것이 확인됐다(§3). 즉 "주석만 다르면 안전하다"는
전제 자체가 이 프로젝트에서는 성립하지 않는다 — I-167이 우려한 그대로 "정규화가 과하면
실제 편집을 가린다"의 실물 사례였다. **그래서 주석 제거는 정규화 규칙에서 뺐다.** 대신
"코드 줄만 비교했을 때 같은가"는 순수 심각도 태그로만 남겨, 보고서에서 뭘 먼저 볼지
정렬하는 데만 쓴다 — **20건 전부를 여전히 "불일치"로 보고한다.**

### 2.2 채택한 유일한 규칙: 파일 끝 트레일링 개행 전부 무시

**원인 확인**: 정확히 1바이트만 다른 사례 2건(`20260724103449`, `20260725040400`)을
바이트 단위로 대조하니 로컬 파일은 `\n`으로 끝나고 원격 `statements[1]`은 끝나지 않는다
— 그 외 모든 바이트가 동일했다. 이 두 파일은 나머지 131건과 함께 최초 whole-file MD5
대조(I-167의 방식)에도 걸렸을 후보였지만, 이 경우만은 정말로 "무편집"이다 — 131건 중
102건은 원격이 트레일링 개행까지 포함해서 저장했고(로컬과 완전 바이트 일치), 이 2건만
그렇지 않았다. 즉 **원격 저장이 트레일링 개행을 일관되게 정규화하는 것도 아니다** — 그때
그때 제출된 문자열 그대로 저장된 것으로 보인다(§5).

**정규화 규칙**: 비교 전 로컬·원격 양쪽에서 `rstrip('\n')`을 적용한다. **문서화 정정
(35일차, BOARD 교차검증)**: 최초 작성 시 이 규칙을 "개행 **1개**만 무시"로 서술했으나,
이건 문서 표현이 구현과 어긋난 것이었다 — `rstrip('\n')`은 파일 끝의 개행 문자를 **몇
개든 전부**(1개든 3개든) 제거한다. BOARD가 트레일링 개행을 3개 추가한 합성 편집으로
실제 동작을 확인해 이 어긋남을 잡았다. **구현이 맞고 문서가 틀렸던 것**이라 구현은
그대로 두고 문서만 정정한다 — 개행이 몇 개 쌓여 있든 파일 끝에서만 SQL 실행 의미가
없는 문자이므로, "1개만"이든 "전부"든 안전성 논증(아래)에는 차이가 없다. **이 이상은
아무것도 정규화하지 않는다.**

**이 규칙이 왜 안전한가(미탐 위험 없음의 근거)**: 트레일링 개행은 정의상 마지막 SQL문
뒤, 파일의 물리적 끝에만 존재한다. SQL 파서는 이를 완전히 무시한다(실행 결과에 영향 없음
— 이 두 파일 다 `grant`/`with check` 문으로 끝나고 그 세미콜론 뒤에는 개행 외 아무 문자도
없다). **문서 중간의 개행은 건드리지 않으므로, 파일 중간 어디에 있는 편집이든 그대로
바이트 차이로 남는다** — 파일 끝에 정확히 위치한, SQL 실행에 영향 없는 트레일링 개행을
(몇 개든) 무시하는 것이 놓칠 수 있는 편집은 "파일 맨 끝에 트레일링 개행만 추가/제거하는
편집"뿐인데, 그런 편집은 애초에 SQL 텍스트에 아무 정보도 더하지 않는다.

### 3.1 `20260724104430` — I-167 자신의 대조군이 실은 대조군이 아니었다

I-167은 이 파일을 "한 번도 사후 편집된 적 없는" 대조군으로 골라, whole-file MD5 불일치의
원인을 "주석 문단 사이 빈 `--` 구분줄이 저장 과정에서 사라졌다"고 진단했다. **바이트
단위로 직접 대조하면 이 진단은 틀렸다:**

```
--- local (현재 저장소 파일, git 이력상 유일한 커밋)
+++ remote (schema_migrations.statements[1])
@@ -1,9 +1,7 @@
 -- Task 027 후속(13일차 교차검증, BOARD): pg_cron 설치 스크립트가 cron.job/cron.job_run_details에
 -- 남기는 PUBLIC 기본 grant(SELECT, job_run_details엔 DELETE도)를 defense-in-depth로 회수한다.
---
--- 실측 결과: 이 프로젝트의 postgres role로는 반영되지 않는다(no-op) — cron.job/cron.job_run_details의
--- 소유자가 postgres가 아니라 supabase_admin이고, postgres는 그 멤버가 아니다(Supabase 관리형 인스턴스는
--- 최종 사용자에게 진짜 슈퍼유저 권한을 주지 않는다). 실효 방어는 cron 스키마 USAGE가
--- anon/authenticated/PUBLIC 어디에도 없다는 것에 의존한다. 상세: docs/decisions/cron-foundation.md 5절.
+-- 현재는 anon/authenticated에 cron 스키마 USAGE가 없어 실질 차단되지만(nspacl 확인),
+-- 향후 누군가 schema USAGE를 부여하면 즉시 로그 삭제까지 가능해지는 잠재 리스크를 지금 끊는다(NFR-011 기본 거부 원칙).
+-- postgres(테이블 소유자)·service_role(명시적 select grant, Task 027)에는 영향 없다.

```

빠진 건 빈 줄 하나가 아니라 **논지가 다른 문단 전체**다. 원격(실제 적용 시점) 주석은
"USAGE가 없어 차단된다"는 defense-in-depth 프레이밍이고, 현재 로컬 주석은 "postgres role
소유가 아니라서 애초에 no-op이다"라는 **정반대에 가까운 결론**(로드맵 문서의 "교차검증
반영: 실측 결과 no-op" 서술과 일치)이다. `git log --follow -p`로 이 파일의 전체 이력을
확인하면 **커밋은 단 1개**뿐이다 — 즉 이 편집은 git 커밋 이전, Task 027 같은 세션 안에서
일어났고 그 사이 원격에 재적용된 적은 없다. SQL 실행문 2줄(`revoke all ...`)은 양쪽이
동일해 기능적 영향은 없지만, **"이미 적용된 파일은 사후 편집하지 않는다"는 규칙을 어긴
사례가 하루 전체 규칙화(34일차) 21일 전인 13일차(Task 027)에 이미 있었다**는 뜻이다.

이 오진단이 남긴 실무적 교훈: **MD5 불일치를 "아마 이런 이유일 것"으로 짐작하지 말고
반드시 라인 단위 diff를 눈으로 봐야 한다.** 이번 감사가 처음부터 "주석 제거 정규화"를
채택하지 않고 §2.1처럼 근거를 요구한 것도 같은 이유다.

## 4. CODE 태그 3건 — 라이브 DB 대조

이 3건은 "코드 줄"(비-`--`, 비-빈 줄) 자체가 로컬과 원격에서 다르다. 셋 다 **그 마이그레이션
버전보다 나중에, 정확히 그 문제를 고치는 이름의 별도 마이그레이션이 이미 존재**했다 —
즉 최초 적용 이후 실제로 재적용된 정정이 있었다는 뜻이다. 문제는 **그 정정이 새 버전으로
갔는데도, 원래 파일(더 이른 버전)의 로컬 내용까지 손으로 바꿔놨다**는 것 — 정정 마이그
레이션 자체는 규칙대로였지만, 그 정정과 "내용을 맞추기 위해" 이미 적용된 이전 파일을
추가로 사후 편집한 것은 규칙 위반이다. `pg_get_functiondef`/`obj_description`/
`col_description`으로 **현재 배포 상태**를 직접 확인해, 라이브 DB가 로컬 파일(최신, 즉
정정 후 값)과 일치하는지 실측했다.

### 4.1 `20260725072923` — `comment on function` 문자열의 이슈 번호

- 로컬(현재)·원격(당시) 모두 `comment on function public.anonymize_expired_deactivated_
  profiles(...)` 문 자체는 같고, 문자열 리터럴 안 이슈 번호만 다르다: 로컬 **I-056** vs
  원격 **I-055**.
- 후속 마이그레이션 `20260725075355_fix_anonymize_job_issue_reference.sql`이 존재하고,
  본문이 정확히 이 정정을 설명한다: "등재 직전 재확인 규칙을 지키지 않고 I-055를 미리
  못박아 뒀는데, 실제 등재 시점엔 BOARD가 이미 I-055(오류 추적)를 먼저 등재해 번호가
  어긋났다. 실제 번호(I-056)로 정정한다 — 기능 변경 없음, 코멘트만." 이 파일 자체는
  로컬=원격 완전 일치(정상적인 새 버전 정정).
- **라이브 실측**: `select obj_description('public.anonymize_expired_deactivated_profiles
  (integer, interval)'::regprocedure, 'pg_proc')` → `...I-056...` — **현재 로컬 파일과
  일치, 원격 072923 원장 값(I-055)과는 불일치**. 기능 영향 없음(주석은 카탈로그 메타데이터,

### 4.2 `20260725142305` — 결정 번호(D-048 vs D-049)

- `comment on column`, `comment on function`, `raise exception` 메시지 3곳 전부에서 로컬은
  **D-049**, 원격은 **D-048**.
- 후속 마이그레이션 `20260725144453_admin_console_042b_fix_decision_number_refs.sql`이

  참조 2건을 실제로 등재하는 결정 번호 D-049(system_admin 식별)로 정정한다. 로직은

  `pg_proc.prosrc`(`profiles_guard_self_status_transition`)의 `raise exception` 메시지
  둘 다 **D-049** — 현재 로컬 파일과 일치.

### 4.3 `20260725142344` — `where` 절 컬럼 한정자(진짜 코드 변경)

- 이 3건 중 유일하게 **주석이 아니라 실행되는 조건절 자체**가 다르다:
  로컬 `where id = v_author_id and public.profiles.status = 'active'` vs
  원격 `where id = v_author_id and status = 'active'`.
- 후속 마이그레이션 `20260725142751_admin_console_042b_fix_ambiguous_status_column.sql`이
  존재: `private.admin_resolve_report`의 `returns table(..., status text)`가 만드는 OUT
  파라미터 `status`가 PL/pgSQL 본문에서 암묵 변수가 되어 위 WHERE절의 `status`와 충돌,
  `42702`(컬럼 참조 모호함) 오류를 냈다는 실측 기록과 함께 `public.profiles.status`로
  명시 한정하는 수정이다 — **이건 진짜 버그 수정**이었다.
- **라이브 실측**: `pg_get_functiondef('private.admin_resolve_report(uuid, text)')` 전문을
  확인 — `public.profiles.status = 'active'`로 한정돼 있다. 현재 로컬 파일과 일치, 원격
  142344 원장 값(비한정 `status`, 버그가 있던 버전)과는 불일치.
- **위험 성격 정정(35일차, BOARD 교차검증)**: 이 컬럼 참조 모호함은 "다른 테이블의 동명
  컬럼과 헷갈릴 수 있다"는 종류가 아니다 — **같은 함수 안에서 만들어지는 OUT 파라미터
  `status`**(`returns table(ok boolean, reason_code text, status text)`가 선언하는 그
  `status`)와 `public.profiles.status` 컬럼이 충돌하는 것이다. PL/pgSQL의
  `variable_conflict` 기본값은 `error`라, 이런 충돌은 **둘 중 하나로 조용히 resolve되지
  않고 무조건 `42702` 예외로 즉시 죽는다.** 즉 비한정 `status`가 원장에 남아 있던 동안의
  실제 위험은 "엉뚱한 행이 조용히 갱신된다"가 **아니라** "`suspend_account` 관리자 액션이
  호출될 때마다 100% 하드 실패한다"였다 — **침묵 오작동이 아니라 즉시 실패**라는 점에서
  이 감사가 다뤄 온 다른 축소·탈락류(RLS 조용한 행 축소, INNER JOIN 조용한 탈락 등)와는
  위험 등급이 다르다: 데이터가 오염되지 않고, 실패가 호출 즉시 드러난다.

**세 건 모두 결론은 같다: 라이브 DB는 지금 안전하다(전부 최신 정정이 실제로 반영돼
있다). 다만 세 건 모두 "정정은 새 버전으로, 원본은 그대로 둔다"는 올바른 절차와 "정정에
맞춰 원본 파일도 손으로 고쳐 둔다"는 규칙 위반이 함께 일어났다** — 결과적으로 원장
(schema_migrations)과 저장소가 갈라진 시점이 25일차(Task 042B 당일)까지 거슬러 올라간다.
34일차 이전까지 아무도 이 갈라짐을 몰랐다.

## 5. 오탐·미탐 판정 근거

이 감사가 채택한 정규화는 "파일 끝 트레일링 개행 전부 무시" 단 하나뿐이다(§2.2). 그 외 어떤 문자도
비교 전에 지우지 않는다. 그래서 오탐·미탐을 각각 이렇게 논증한다.

**오탐(정규화가 실제로는 무편집인 파일을 불일치로 잘못 표시하는 경우) 없음의 근거**: 채택한
유일한 정규화(트레일링 개행)는 두 파일에서 "이 정규화를 걸었을 때만 완전 바이트 일치"로
직접 검증됐다(§2.2) — 즉 정규화를 걸지 않았다면 이 2건이 불필요하게 §3 표에 올라 20건이
아니라 22건이 됐을 것이다. 반대로 이 정규화가 실제 편집을 가리는 경우는 논리적으로 없다
— 트레일링 개행은 정의상 파일 중간의 어떤 내용도 대표하지 않기 때문이다.

**미탐(사후 편집이 있는데 이 규칙이 놓치는 경우) 없음의 근거 — 실측 두 갈래**:

1. **실제 34일차 편집 파일 자체가 여전히 감지 대상인지**: `20260731010558`·`20260731013305`
   두 파일 다 되돌림이 끝난 현재 상태에서 로컬=원격(§0 표에 포함되지 않음 — 정상). 34일차
   당시의 "정정된 정규형 논증이 반영된" 오염 상태를 재현하려면 그 시점의 git 커밋이
   필요한데, `git log --follow`로 확인한 결과 두 파일 다 **git 커밋은 1개뿐**(현재의
   되돌려진 최종 상태만 기록됨 — 오염 상태는 커밋 전 세션 안에서만 존재했다 이 프로젝트
   전체의 반복 패턴, §3.1·§4와 동일). git 이력만으로 오염 텍스트를 복원할 수 없어, 대신
   합성 테스트로 검증했다(아래 2번). **파일 자체는 재편집하지 않았다** — 스크립트 안
   메모리상의 문자열 치환으로만 시험했다.
2. **합성 미탐 시험**: `20260731010558`의 현재(정상) 내용에서 주석 문장 한 곳만 다른
   단어로 바꾼 사본을 메모리에서 만들어 원격 값과 비교했다 — 결과: 정규화 후에도
   **불일치로 감지됨**(코드 줄은 동일해 COMMENT 태그가 붙지만, §3 표에는 여전히
   올라온다). 이 저장소의 방식은 "위험해 보이는 줄만 골라 지우는" 방식이 아니라
   "정확히 증명된 무해한 바이트(트레일링 개행)만 지우는" 방식이라, **정규화가 편집을
   가릴 수 있는 경로 자체가 없다** — 코드 태그는 우선순위 정렬에만 쓰이고 불일치 판정
   자체를 걸러내지 않기 때문이다.
3. **미탐 시험 확장(35일차, BOARD 교차검증)**: 위 2번(주석 단어 치환) 1종만으로는 부족하다고
   보고 BOARD가 합성 편집 5종으로 넓혀 재시험했다 — 전부 로컬 파일을 재편집하지 않고
   메모리상 사본으로만 시험:
   - 파일 중간 공백 삽입 → **탐지됨**
   - 파일 전체 CRLF 변환(`\n` → `\r\n`) → **탐지됨**
   - 유니코드 NFD 정규화(조합형/완성형 변환) → **탐지됨**
   - 파일 끝 트레일링 개행을 여러 개 추가 → **탐지 안 됨(설계대로)** — §2.2가 명시한
     유일한 정규화 대상이 정확히 이것이다
   - 트레일링 개행 바로 앞 문자(파일의 실질적 마지막 문자)를 변조 → **탐지됨**
   
   5종 중 놓치는 유형은 정확히 1개 — "파일 맨 끝의 순수 개행 추가/제거"뿐임을 실측으로
   확정했다. 이건 §2.2가 처음부터 "이 정규화가 놓칠 수 있는 유일한 편집은 트레일링
   개행만 추가/제거하는 것뿐이고, 그런 편집은 SQL 텍스트에 정보를 더하지 않는다"고 미리
   논증했던 것과 정확히 일치한다 — 즉 이 시험은 §2.2의 안전성 논증을 반증하려다 실패하고
   오히려 뒷받침한 것이다.

**§2.1에서 기각한 "주석 줄 제거" 규칙이 왜 위험했는지(반면교사)**: 그 규칙을 그대로
정규화로 채택했다면 17건이 "무편집"으로 조용히 사라지고, 3건의 CODE 사례 중에서도
`comment on function/column`처럼 SQL문 형태를 갖춘 줄은 잡았겠지만 만약 어느 사후 편집이
`-- ` 줄 안에서만 일어났다면(실제로 §3.1의 `20260724104430`이 그 예다) **완전히
놓쳤을 것**이다. 이것이 이번 감사가 "코드만 비교하는 규칙"을 정규화가 아니라 태그로만
격하시킨 이유다.

## 6. 재실행 가능한 스크립트

- `dump_remote_statements.sql` — supabase MCP `execute_sql`(또는 SQL 편집기)로 실행해
  원격 전건을 JSON으로 받는다. 결과가 도구 토큰 한도를 넘으면 자동 저장된 파일 경로를
  다음 스크립트에 그대로 넘길 수 있다.
- `audit_compare.py` — 로컬 `supabase/migrations/`와 위 JSON을 받아 §2.2 규칙으로 비교하고
  §3과 동일한 형식의 표를 출력한다(불일치가 있으면 exit code 1). 원격 접근을 하지 않는
  순수 로컬 스크립트라 반복 실행 비용이 없다. 사용법은 스크립트 상단 docstring 참고.

  ```
  python3 docs/design/migration-integrity-audit-35/audit_compare.py \
    --json <원격 덤프.json> \
    --migrations-dir supabase/migrations
  ```

- 이번 감사에서 실제로 만든 원격 덤프 원본(536KB)은 저장소에 커밋하지 않았다 — 저장소
  용량과 §3 표(md5 포함)로 이미 재현 가능한 내용의 중복이기 때문이다. 재검증이 필요하면
  위 SQL을 다시 실행하면 된다(각 버전의 `statements`는 그 마이그레이션이 다시 적용되지
  않는 한 불변이므로, §3의 20건에 대한 원격 값은 이 문서가 남긴 md5로 언제든 재확인 가능).

## 7. 왜 `stmt_count`가 항상 1인가 (추정, 확정 아님)

이 프로젝트의 모든 마이그레이션에서 `array_length(statements, 1) = 1`이었다. 표준
`supabase db push`/CLI 마이그레이션 흐름은 파일을 문장 단위로 쪼개 여러 원소로 저장하는
것으로 알려져 있으나, 이 저장소는 전부 `mcp__supabase__apply_migration`으로 적용됐다
(I-051 참고 — 이 도구는 로컬 파일을 쓰지 않는다). **가장 그럴듯한 설명은 이 MCP 도구가
파일을 문장 단위로 분할하지 않고, 호출 시점에 전달한 SQL 텍스트 전체를 통째로 하나의
원소로 기록한다는 것**이다 — 이 가설은 §2.2에서 확인한 사실(원격 값이 제출 당시 텍스트를
"있는 그대로" 담고 있고, 트레일링 개행 유무조차 파일마다 다르게 남아 있어 별도의 정규화
서버 로직이 있다고 보기 어렵다)과 정합한다. 다른 프로젝트/다른 적용 경로(CLI `db push`
등)를 쓴다면 이 가정이 깨질 수 있으므로, 재사용 전 `dump_remote_statements.sql`의 주석대로
`array_length`를 먼저 확인할 것.

## 8. 남은 리스크

1. **`schema_migrations.statements`는 원장이지만, 원장 자체가 "적용 당시의 진실"이라는
   보장은 이 감사 범위 밖이다.** 이번 20건에서는 라이브 DB(§4)가 항상 로컬 파일(최신) 쪽과
   일치했지만, 이건 "누군가 나중에 제대로 된 정정 마이그레이션을 추가했기 때문"이지
   구조적 보장이 아니다. 정정 마이그레이션 없이 파일만 고친 사례가 있었다면 라이브 DB와
   로컬 파일이 갈라진 채로 지금까지도 발견되지 않았을 것이다 — 이번에 그런 사례는
   **없었다**(3건 모두 대응하는 정정 마이그레이션을 찾았다)는 것이 다행일 뿐, 앞으로도
   그러리라는 보장은 아니다.
2. **이 대조는 일회성이다.** 앞으로 새 마이그레이션이 추가될 때마다 이 스크립트를 다시
   돌리지 않으면 같은 종류의 드리프트가 또 조용히 쌓인다 — CI가 없는 상태(R-002)라
   자동화되지 않는 한 사람이 기억해서 돌려야 한다. 후속 이슈로 제안한다(초안 참고).
3. **`schema_migrations` 원장 자체를 지금 와서 고칠지는 이번 감사의 판단 밖이다.** 20건의
   "실제로는 다른 텍스트가 적용됐다"는 사실을 원장에 반영(예: 정정 마이그레이션 추가)할지,
   그냥 알려진 과거 드리프트로 문서에만 남길지는 팀장 판단이 필요하다 — DDL 승인 없이
   임의로 새 마이그레이션을 추가하지 않았다(배정 규칙 준수).
4. **`docs/decisions/cron-foundation.md`가 인용하는 "5절" 내용이 실제로 적용된 코멘트
   (§3.1의 원격 값)와 다르다.** 문서가 로컬 파일(현재, no-op 설명)과는 정합하지만, 만약
   누군가 원장 텍스트를 신뢰 기준으로 삼아 재검토하면 혼란의 소지가 있다 — 문서 자체를
   고칠 필요는 없다(로컬 파일이 최신 진실이라는 34일차 이후 규칙과 일치), 다만 존재를
   기록해 둔다.
